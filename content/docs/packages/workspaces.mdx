title: Workspaces
description: "Manage related packages with shared installation, local dependencies, filters, and deployment output."
---

A workspace groups packages under one root. Each member keeps its own dependencies, scripts, and version. LPM CLI shares the root lockfile and local package links.

```bash
# Install the workspace from its root
lpm install

# Add a dependency to one member
lpm install zod --filter web

# Preview the members that depend on shared
lpm filter '...shared'

# Run tests for changed members and their dependents
lpm run test --affected --base origin/main
```

Registry dependencies can come from npm, LPM.dev Registry, or private registries. Workspace dependencies use local packages.

## Declare members

```json title="package.json at the workspace root"
{
  "name": "my-workspace",
  "private": true,
  "workspaces": ["packages/*", "apps/*"]
}
```

The object form is also supported:

```json
{
  "workspaces": {
    "packages": ["packages/*", "apps/*"]
  }
}
```

Each matching directory must contain a `package.json`. Use `*` for one path segment and `**` for recursive patterns.

LPM CLI combines patterns from `package.json > workspaces` and `pnpm-workspace.yaml > packages`. Duplicate patterns are processed once.

```yaml title="pnpm-workspace.yaml"
packages:
  - packages/*
  - apps/*
```

A missing YAML file is allowed. An invalid or oversized file fails workspace discovery. Root manifests, member manifests, and the YAML file each have a 16 MiB limit.

Release and version scans also bound pattern counts, directory entries, and path storage. See [project size limits](/docs/project-setup#local-configuration-size-limits).

`lpm.json` does not declare workspace members. It can define [tasks](/docs/dev/run) for those members:

```json title="packages/web/lpm.json"
{
  "tasks": {
    "build": {
      "dependsOn": ["^build"],
      "outputs": ["dist/**"]
    }
  }
}
```

Each member defines its own tasks. Members do not inherit root task definitions. `^build` requires upstream members to finish their build tasks first. Each upstream member must define that task.

```bash
lpm run build --filter web
```

## Install and change dependencies

At the workspace root, [`lpm install`](/docs/packages/install#workspaces) refreshes the members and the root. Inside a member, a bare install stays local to that member.

```bash
# Refresh the whole workspace from a member
lpm install --recursive

# Refresh only the current project
lpm install --no-recursive

# Refresh selected members and their required local dependencies
lpm install --recursive --filter web
lpm install --recursive --filter-prod web

# Add a dependency to a member or the root
lpm install zod --filter web
lpm install typescript --save-dev -w

# Remove a dependency from a member
lpm uninstall zod --filter web
```

Filtered refreshes include the required workspace dependency closure. They exclude unrelated members and the root. `--filter-prod` excludes development edges from that selection.

`--recursive` refreshes existing manifests. It does not add package arguments to every member.

For mutations across multiple members, interactive terminals request confirmation. `--yes`, JSON mode, and non-interactive input skip that prompt.

Workspace installations use the isolated layout by default. See [dependency layouts](/docs/packages/dependency-graph) for overrides and visibility rules.

## Workspace protocol

```json title="packages/web/package.json"
{
  "name": "web",
  "dependencies": {
    "@my-co/shared": "workspace:*"
  }
}
```

A `workspace:` reference requires a matching local package. The provider can be a member or the named package at the workspace root.

| Specification | Requirement |
| --- | --- |
| `workspace:*` | Any local version. |
| `workspace:^` | Use the local version with caret semantics. |
| `workspace:~` | Use the local version with tilde semantics. |
| `workspace:^1.2.0` | The local version must satisfy `^1.2.0`. |

These specifications remain unchanged under [save policy](/docs/packages/save-policy).

A `workspace:` self-reference in production, optional, or peer dependencies fails. A dev-only self-reference is excluded from installation.

Matching local packages can also satisfy compatible ordinary version ranges, including transitive registry dependencies. A nonmatching version requires another candidate.

## Shared lockfile

The root `lpm.lock` records the workspace graph and a separate dependency view for each importer. Member commands use their own view.

A successful recursive install absorbs legacy member lockfiles into the root lockfile and removes obsolete member companions. Workspace lockfiles are TOML-only.

Manifest and lockfile changes commit after the selected installation succeeds. A failure restores those files. Changes inside `node_modules` can remain until the next install repairs them.

After a root catalog or override change, refresh the workspace and commit the root manifest with its lockfile:

```bash
lpm install
```

For CI, use a frozen install:

```bash
lpm install --frozen-lockfile
```

See [lockfile behavior](/docs/packages/lockfile) for frozen checks, migration, and recovery.

## Filter grammar

Filters select member names or paths. Multiple positive expressions select their union. Each filter group requires a positive expression before exclusions can apply.

| Expression | Selected members |
| --- | --- |
| `web` | The exact package name. |
| `@scope/*` | Names under that scope. |
| `./apps/*` | Paths that match the glob. |
| `{./apps/web}` | The exact path. |
| `@scope/*{./apps/web}` | Both the name and path conditions. |
| `[origin/main]` | Members with files changed since that Git reference. |
| `web...` | `web` and its dependencies. |
| `web^...` | Dependencies of `web`, excluding `web`. |
| `...web` | `web` and its dependents. |
| `...^web` | Dependents of `web`, excluding `web`. |
| `!web` | Exclude `web` from that filter group. |

An exact name does not perform substring matching. To select `@babel/core` by its suffix, use `*/core`.

```bash
lpm filter 'web...' --explain
lpm filter --filter-prod '...shared' --json
lpm filter web --fail-if-no-match
```

`--filter-prod` follows dependencies, optional dependencies, and peer dependencies. It excludes development edges.

The regular filter group, production filter group, and `--affected` group are evaluated separately and then combined. An exclusion in one group does not remove members selected by another group.

## Select changed packages

```bash
lpm filter '[origin/main]'
lpm filter '...[origin/main]'
lpm run test --affected --base origin/main --fail-if-no-match
```

`[ref]` selects directly changed members. `...[ref]` and `--affected` also include dependents. The default affected base is `main`.

Git paths are relative to the workspace root, including workspaces nested inside a larger repository. Changes outside that workspace do not select its members.

A file move selects both its former member and its new member. A changed root file outside any member selects every member. The comparison includes tracked changes against the base reference. It does not include untracked files.

A missing or invalid reference fails the command. If CI has a shallow clone, fetch the base reference before selection.

```bash
lpm run test --affected --base origin/main \
  --changed-files-ignore-pattern '**/README.md' \
  --test-pattern '**/*.test.js'
```

Ignore patterns remove paths before selection. Test patterns keep the changed member but do not add dependents for changes that contain only tests.

Set shared patterns in the root configuration:

```toml title="lpm.toml"
[workspace]
changed-files-ignore-pattern = ["**/README.md", "docs/**"]
test-pattern = ["**/*.test.js", "**/*.spec.ts"]
```

CLI patterns append to these defaults. There is no one-run flag that clears the project patterns.

## Commands and selection options

| Command | Selection options |
| --- | --- |
| [`lpm install`](/docs/packages/install) | Filters, `-w`, recursive refresh, and `--fail-if-no-match`. |
| [`lpm uninstall`](/docs/packages/uninstall) | Filters, `-w`, and `--fail-if-no-match`. |
| [`lpm run`](/docs/dev/run), [`lpm test`](/docs/dev/test), [`lpm bench`](/docs/dev/bench), [`lpm lint`](/docs/dev/lint), [`lpm fmt`](/docs/dev/fmt), [`lpm check`](/docs/dev/check) | Filters, `--all`, `--affected`, `--base`, and `--fail-if-no-match`. |
| [`lpm filter`](#filter-grammar) | Positional expressions, production filters, `--explain`, and `--fail-if-no-match`. |
| [`lpm deploy`](#lpm-deploy) | A regular or production filter that selects exactly one member. |

`--all` cannot combine with filters or `--affected`. Git ignore and test patterns apply to commands with Git-based selection.

## Catalogs

```json title="package.json at the workspace root"
{
  "catalogs": {
    "default": { "react": "^19.0.0" },
    "testing": { "vitest": "^3.0.0" }
  }
}
```

```json title="packages/web/package.json"
{
  "dependencies": { "react": "catalog:" },
  "devDependencies": { "vitest": "catalog:testing" }
}
```

Members use the root catalog declarations. After a catalog change, refresh the workspace to update the lockfile.

```bash
lpm catalog list --unused
lpm catalog show --resolved --json
```

See [`lpm catalog`](/docs/packages/catalog) for YAML declarations and cleanup. See [save policy](/docs/packages/save-policy#catalogs-take-precedence) for automatic conversion.

## `lpm deploy`

```bash
lpm deploy /prod/api --filter api --dry-run
lpm deploy /prod/api --filter api
lpm deploy /prod/api --filter api --no-optional
lpm deploy /prod/api --filter api --dev
```

[`lpm deploy`](#lpm-deploy) copies a member's publishable files and its selected `workspace:` sources. It then installs the output's dependencies. The output directory must neither contain the workspace nor sit inside it.

The default selects production and optional dependencies. `--dev` selects the member's development dependencies instead. Copied providers still use their production dependencies.

`--no-optional` omits optional dependencies, including duplicate names in regular dependencies. An optional declaration takes precedence over a regular declaration.

Selected dependencies declared with `workspace:` go under `.lpm/deploy-workspace/`. Their copied manifests use relative `file:` references. This includes named root providers and peer-only local references.

Catalog references use the root catalog declarations. The copied manifests contain the declared catalog specifications.

Existing `file:`, `link:`, and `portal:` paths are not relocated. Compatible ordinary version ranges do not copy local workspace providers through this mechanism.

A copied peer-only source is not an automatically installed root dependency. The consuming project must supply its required peers.

The file selection uses `files`, then `.npmignore`, then `.gitignore`. The deny list applies at every directory depth, including explicit `files` entries:

- Every name that starts with `.env`, including secret directories and example files.
- `node_modules`, `.lpm`, `lpm.lock`, and `lpm.lockb`.
- `.git`, `.gitignore`, `.npmignore`, `.gitattributes`, `.svn`, and `.hg`.
- `.DS_Store` and `Thumbs.db`.

The output includes its own store and lockfile. Unix installations make internal `node_modules` links relative.

Source files can use hardlinks. Later writes to a shared file can also change the original workspace file. Copy the output across filesystems or into an image before editing it.

On Unix, source symlinks remain symlinks, including links outside the copied package. Windows skips source symlinks and junctions. Review these paths before moving the output to another machine.

`--force` deletes and recreates the output directory. A dry run writes no files. JSON output contains one deployment result.

```bash
lpm deploy /prod/api --filter api --json
```
