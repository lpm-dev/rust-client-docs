LPM CLI separates permission to run dependency scripts from source analysis, vulnerability reports, and publisher checks. Each check answers a different question.

These controls work with npm, LPM.dev Registry, and private registries. Only `@lpm.dev/*` packages always use LPM.dev Registry.

```bash
# Install dependencies, then inspect blocked scripts
lpm install
lpm approve-scripts --list

# Fail on High and Critical vulnerabilities
lpm audit --level high --fail-on vuln
```

## What happens by default

| Control | Default behavior |
| --- | --- |
| Root-project lifecycle | Bare [lpm install](/docs/packages/install) runs the project's install lifecycle, including `prepare`. |
| Dependency lifecycle | Scripts require approval. The relevant phases are `preinstall`, `install`, and `postinstall`. |
| Script sandbox | Approved scripts run with filesystem restrictions and a filtered environment. Outbound network access is allowed. |
| Install-time source analysis | Off. Enable it separately to inspect package source during installation. |
| Automatic audit | Off. An enabled audit after installation reports findings without turning them into an install failure. |
| Advisor | Off. Triage can use an optional advisor to review scripts. |
| Release cooldown, signature checks, trust policy, typosquat guard, LPM Firewall | Opt-in controls with separate configuration. |

A successful install does not mean that an audit passed. Use [lpm audit](/docs/packages/audit) as an explicit CI gate.

## Review and run dependency scripts

```bash
# Inspect one package before saving an approval
lpm approve-scripts esbuild --dry-run
lpm approve-scripts esbuild

# Run approved scripts
lpm rebuild
```

[lpm approve-scripts](/docs/packages/approve-scripts) saves trust. [lpm rebuild](/docs/packages/rebuild) runs eligible scripts.

New artifact approvals bind the package name, version, integrity, and lifecycle script hash. The hash includes recognized local JavaScript delegates and reachable imports.

A changed artifact needs another review. Legacy name approvals and [trusted scopes](/docs/packages/trust#lpm-trust-lifecycle-scope) also exist, with broader coverage.

The approval queue includes blocked dependency `preinstall`, `install`, and `postinstall` scripts. Other phases, such as dependency `prepare`, do not enter this queue.

### Choose a script policy

| Policy | Eligible dependency scripts |
| --- | --- |
| `deny` | Explicitly trusted packages only. This is the default. |
| `triage` | Explicitly trusted packages, recognized safe commands, and packages approved by the advisor for this install. |
| `allow` | All dependency lifecycle scripts. |

Policy precedence is CLI flags, project `lpm.scriptPolicy`, user `script-policy`, then the default.

```bash
lpm install --triage --advisor=none
lpm config scripts --set deny
```

Eligibility does not itself run a script. Installation uses auto-build, configured auto-build, or an all-trusted package set to decide when to run eligible scripts.

The `allow` policy also requests automatic execution. Project `lpm.scripts.denyAll` suppresses dependency execution even if approvals exist.

Weaker policies can require [security approval](/docs/infra/security). An unattended flag cannot bypass the approved security floor.

### Understand triage labels

Green, Amber, and Red describe static script classifications. They are separate from saved trust.

- **Green:** The command matches a recognized pattern. A local delegated file still needs review before automatic execution.
- **Amber:** The script needs explicit approval or an advisor decision.
- **Red:** Triage does not approve it automatically. A package with any Red phase is excluded from advisor review.

A matching repository URL can affect the displayed label. It does not approve delegated code. Explicit package or scope trust can authorize scripts with any label.

## Keep sandbox policy separate

| Sandbox mode | Effect on eligible scripts |
| --- | --- |
| `default` | Filesystem restrictions, filtered environment, outbound network allowed. |
| `strict` | The same restrictions, with outbound network denied. |
| `none` | No script containment or inherited-environment filtering. |

Sandbox mode controls how an eligible script runs. It does not grant script approval.

An approved `allow-degraded` setting can continue without full isolation when platform support is unavailable. This can include missing network isolation in strict mode.

```bash
lpm rebuild --strict-sandbox
```

Platform restrictions and permitted paths differ. See [sandbox configuration](/docs/reference/lpm-toml#sandbox) and the [script configuration](/docs/reference/package-json-lpm#the-lpmscripts-block).

## Inspect source behavior

```bash
lpm config source-analysis --set true
lpm --verbose install
lpm audit
lpm query ':eval:scripts'
```

Install-time source analysis inspects package code without running it. The install summary reports findings from the installed files and separately configured Registry enrichment.

Registry enrichment uses matching installed-version metadata. Missing or mismatched versions do not inherit findings from `latest`.

The summary is informational. `--no-security-summary` skips the post-install source scan, Registry enrichment, and report. It does not change script policy or explicit audits.

Behavioral tags describe capabilities and source patterns. Network access alone does not prove data theft. Environment access alone does not prove secret exposure.

[lpm audit](/docs/packages/audit) combines source findings with vulnerability and Registry reports. [lpm query](/docs/packages/query) selects packages from its own inventory and analysis.

[lpm trust](/docs/packages/trust) inspects saved approvals and trust changes. These commands have different inventories and failure rules.

Local source analysis does not upload package source. Full analysis covers files up to 4 MiB. Larger files receive samples.

Each package has a 50 MiB scan budget and a 5,000-file limit. Missing inputs, unsupported syntax, or exceeded limits prevent a clean audit.

See [source coverage](/docs/packages/audit#source-coverage) for report fields and recovery. Disabling install-time analysis does not disable explicit audits.

## Check vulnerabilities and publisher evidence

```bash
# Known vulnerabilities
lpm audit --fail-on vuln

# Hardcoded credentials are a separate scan
lpm audit --secrets --fail-on secrets

# npm-compatible registry signatures
lpm audit signatures
```

Vulnerability requests send package names and versions outside `@lpm.dev/*` to OSV, including names from private registries.

LPM.dev Registry supplies findings for its own packages. See [audit network requests](/docs/packages/audit#inventory-and-network-requests) before use with confidential inventories.

| Optional control | Purpose | Configure |
| --- | --- | --- |
| Release cooldown | Avoid recently published versions. Strict mode also covers transitive dependencies and lockfile replay. | [Release age](/docs/infra/config#increase-the-release-cooldown) |
| Registry signatures | Check npm-compatible registry signatures and artifact integrity. Missing required evidence fails installation. | [Signature checks](/docs/packages/audit#registry-signatures) |
| Trust policy | Reject weaker publisher evidence or loss of verified artifact provenance. | [Install trust policy](/docs/packages/install#registry-signatures-and-trust-policy) |
| Provenance drift | Compare publisher identity with a saved approval. Changed or missing evidence can require another review. | [Script approvals](/docs/packages/approve-scripts) |
| Typosquat guard | Detect suspicious new direct dependency names without a network request. | [Typosquat policy](/docs/reference/lpm-toml#typosquat-policy) |
| LPM Firewall | Check selected public npm versions against package verdicts. `monitor` warns and `enforce` blocks according to policy. | [Firewall for npm](/docs/guides/firewall) |

These controls have separate scopes. Registry signature checks skip `@lpm.dev/*` and non-registry sources. LPM Firewall does not replace your npm registry.

## Use an optional advisor

```bash
lpm install --triage --auto-build --advisor=ollama

# Change the local Ollama model for this invocation
LPM_TRIAGE_OLLAMA_MODEL=llama3.2 lpm install --triage --advisor=ollama

# Keep triage but disable the advisor for one invocation
lpm install --triage --advisor=none
```

Supported providers are `none`, `claude-cli`, `codex`, and `ollama`. Precedence is `--advisor`, project `lpm.triageAdvisor`, user `triage-advisor`, then `none`.

The advisor reviews every phase that needs automatic approval, including recognized delegated scripts. All reviewed phases must approve before the package qualifies.

A missing provider or failed preflight produces a warning. A failed individual classification withholds approval. Installation can continue with scripts blocked.

### Data sent to the provider

The prompt contains package coordinates, lifecycle commands, the repository URL when present, and referenced script text.

Referenced-file context is limited to one level and 32 KiB per file. This context is narrower than the complete script hash.

`claude-cli` and `codex` use their configured services. Ollama uses the local server. Select a provider that matches your source-disclosure requirements.

<a id="verdict-cache" />

### Cached decisions and temporary approvals

The execution approval lasts for the current install. It does not write a persistent package trust entry.

Advisor verdicts are cached separately for 30 days by default. The cache includes reviewed content, the complete script hash, prompt template, and provider identity.

Ollama's configured model and endpoint also identify its cache. Changing the model selects a new cache entry.

The provider binary version is part of the identity. It does not guarantee an unchanged remote model or unchanged model weights under an existing name.

```bash
# Request a fresh decision without reading or writing the verdict cache
LPM_L4_CACHE=0 lpm install --triage --advisor=ollama
```

`LPM_L4_CACHE_PATH` changes the cache location. `LPM_L4_CACHE_TTL_SECS` changes the expiry period.

An approved package stays in the review queue if its scripts do not run, such as when `denyAll` suppresses auto-build.

## Apply a CI policy

```bash
lpm install --frozen-lockfile
lpm audit --level high --fail-on vuln
lpm audit --secrets --fail-on secrets
lpm query ':credential-exfiltration' --assert-none
```

These checks do not prompt. The audit exits unsuccessfully for policy failures or incomplete scans. Query assertions fail when the selector matches packages.

For a reusable check, define an uncached task:

```json title="lpm.json"
{
  "tasks": {
    "security:audit": {
      "command": "lpm audit --level high --fail-on vuln",
      "cache": false
    }
  }
}
```

```bash
lpm run security:audit
```

`lpm.json` has no dedicated security policy block. The task contains the command and flags. `cache: false` requests a current report each time.

## Recover from a blocked operation

| Result | Action |
| --- | --- |
| Dependency scripts are blocked | Inspect [lpm approve-scripts --list](/docs/packages/approve-scripts), review the package, then use [lpm rebuild](/docs/packages/rebuild). |
| Approval no longer matches | Inspect the changed artifact and save a new approval only after review. |
| `security_approval_required` | Inspect [lpm security status](/docs/infra/security). Use the suggested scoped unlock only for an intended exception. |
| Advisor unavailable or uncertain | Keep scripts blocked or review them explicitly. |
| Incomplete source scan | Read the [coverage report](/docs/packages/audit#source-coverage) and restore missing inputs or inspect unsupported files. |
| Known vulnerability | Preview [lpm audit fix --dry-run](/docs/packages/audit#fixing-vulnerabilities), then review the proposed updates. |
