---
title: ~/.lpm/config.toml
description: Set user defaults for installs, verification, lifecycle scripts, workspace commands, and tunnels.
---

`~/.lpm/config.toml` stores user defaults for LPM CLI across projects.
Each setting has its own precedence rules. Security controls also depend on approved machine settings and managed policy.

```bash
lpm config set save-prefix '~'
lpm config get save-prefix
lpm config list --json
lpm config unset save-prefix
```

Use [`lpm config`](/docs/infra/config) for supported changes.
Edit the file directly for arrays and policy extensions.
Use [`lpm.toml`](/docs/reference/lpm-toml) or [`package.json > lpm`](/docs/reference/package-json-lpm) for supported project defaults.

## File location

| Platform | Default path |
| --- | --- |
| macOS and Linux | `~/.lpm/config.toml` |
| Windows | `%USERPROFILE%\.lpm\config.toml` |

[`LPM_HOME`](/docs/reference/env-vars#filesystem-layout) moves the configuration file with the store, cache, and global installation root.
The file is created on the first configuration write. A missing file supplies no user overrides.
Configuration reads have a 16 MiB limit.
Security-sensitive commands reject read errors, malformed TOML, and invalid security controls before applying them.
Individual settings have additional validation rules described below.

## Known keys

Start with the settings that your machine needs:

```toml title="~/.lpm/config.toml"
save-prefix = "~"
workspace-concurrency = 4

[sandbox]
mode = "default"
allow-degraded = false
```

### Save policy and workspace commands

| Key | Accepted value | Default | Behavior |
| --- | --- | --- | --- |
| `save-prefix` | `"^"`, `"~"`, `""` | `"^"` | Prefix for newly saved resolved versions. Empty means exact. |
| `save-exact` | Boolean | `false` | Save exact versions regardless of the prefix. |
| `workspace-concurrency` | Positive integer or decimal string | Host parallelism | Concurrent packages for workspace run, test, and bench commands. |

Project `lpm.toml` overrides each save key independently.
Explicit save flags take precedence. Explicit dependency specifications and existing entries have separate preservation rules.
See [Save policy](/docs/packages/save-policy).

Workspace concurrency resolves from the CLI flag, workspace-root `lpm.toml`, this file, then host parallelism.
If host parallelism is unavailable, the fallback is four.

```bash
lpm config set workspace-concurrency 4
lpm run build --all --workspace-concurrency 2
```

### Installation

| Key | Type | Default | Behavior |
| --- | --- | --- | --- |
| `linker` | `"hoisted"` or `"isolated"` | Automatic | Node modules layout. See [linker precedence](#exception--linker). |
| `engine-strict` | Boolean | `true` | Enforce supported project and dependency engine requirements. False changes failures to warnings. |
| `strict-peer-dependencies` | Boolean | `false` | Fail on missing required peers, incompatible peer versions, and peer conflicts. |
| `auto-install-peers` | Boolean | `true` | Install missing non-optional peers at the project root. |
| `auto-install-lpm-skills` | Boolean | `true` | Reconcile package skills from installed `@lpm.dev/*` packages. |
| `noSkills` | Boolean | `false` | Legacy inverse of automatic skill installation. The canonical key takes precedence. |
| `install-time-source-analysis` | Boolean | `false` | Analyze package source during extraction and for the install summary. |
| `fetch-lpm-security-insights` | Boolean | `true` | Use LPM.dev Registry security and lifecycle data for its packages. |
| `audit-after-install` | Boolean | `false` | Add an audit summary after a successful install. Findings do not fail installation. |
| `noSecuritySummary` | Boolean | `false` | Hide the human-readable install security summary. |
| `noEditorSetup` | Boolean | `false` | Accepted compatibility setting with no current effect on installation. |

`engine-strict` uses the workspace-root project value before this file. `--no-engine-strict` overrides both.
Peer settings use the project value before this file. Explicit strict-peer flags override both sources.

Automatic package skills resolve from `--skills` or `--no-skills`, the canonical user key, inverted `noSkills`, then `true`.
The configuration command removes the legacy key when it writes the canonical setting.
Disabling automatic skills does not delete existing skills or affect explicit [`lpm skills add`](/docs/packages/skills).

Source analysis and Registry insights are independent.
Re-enabling source analysis fills missing or outdated analysis caches from existing package bytes.
[`lpm audit`](/docs/packages/audit) can still analyze packages while install-time analysis is disabled.

Audit-after-install resolves from its CLI flags, a valid `LPM_AUDIT_AFTER_INSTALL` value, this file, then `false`.
An invalid environment value falls back to this file.
`noSecuritySummary` combines with its CLI flag: either true value hides the summary.

### Lifecycle scripts and sandbox

| Key | Accepted value | Default | Behavior |
| --- | --- | --- | --- |
| `script-policy` | `"deny"`, `"allow"`, `"triage"` | `"deny"` | Dependency lifecycle execution policy. |
| `triage-advisor` | `"none"`, `"claude-cli"`, `"codex"`, `"ollama"` | `"none"` | Optional advisor for triage decisions. |
| `autoBuild` | Boolean | `false` | Request an automatic rebuild after installation. |
| `force-security-floor` | Boolean | `false` | Preserve configured security floors and suspend saved dependency script approvals. |
| `sandbox.mode` | `"default"`, `"strict"`, `"none"` | `"default"` | Requested dependency lifecycle sandbox mode. |
| `sandbox.allow-degraded` | Boolean | `false` | Permit reduced containment when full containment is unavailable. |
| `script-read-allow` | String array | `[]` | Propose reads of individual protected project files. Requires script approval. |
| `max-sandbox-write-roots` | Absolute path array | `[]` | Bound project requests for writes outside the project. Requires script approval. |

Script policy and advisor selection resolve from CLI flags, project values, this file, then defaults.
The advisor runs only for triage. Execution approvals last for one install. Verdict caching is separate.

`autoBuild` combines with the CLI and project values: any true value requests the rebuild.
An allow policy or a fully trusted pending set can also trigger a rebuild. `denyAll` still prevents execution.

Sandbox mode resolves from CLI flags, true `LPM_STRICT_SANDBOX`, project `lpm.toml`, this file, then its default.
Sandbox degradation uses the project value before this file.
All reductions remain subject to [security approval](#security-sensitive-keys-are-proposals).

Read allowances combine with project `sandboxReadAllow` entries.
Directories, symlinks, and paths outside the project are rejected.
Write roots can use `~/`. Relative roots are ignored.
Protected system and credential paths remain denied. See [script capabilities](/docs/reference/package-json-lpm#the-lpmscripts-block).

### Release cooldown

| Key | Accepted value | Default | Behavior |
| --- | --- | --- | --- |
| `minimum-release-age-secs` | Nonnegative integer or decimal string | `0` | Minimum package age in seconds. Zero disables the cooldown. |
| `release-age-policy` | `"direct"` or `"strict"` | `"direct"` | Check direct dependencies only, or also transitives and lockfile replay. |
| `minimum-release-age-exclude` | String array | `[]` | Package names, exact package versions, or `@scope/*` exceptions. |
| `allowNew` | Boolean | `false` | Request a cooldown bypass during installation. Requires authorization when the cooldown applies. |

Minimum age resolves from the CLI flag, project value, this file, then zero.
The age policy resolves from the project value, this file, then `direct`. The string `"default"` also means `direct`.
Exclusions merge CLI entries, project entries, and user entries, with duplicates removed.
`allowNew` combines with `--allow-new`.

```bash
lpm config set minimum-release-age-secs 86400
lpm config release-age-exclude add @acme/internal
lpm install --min-release-age 2d
```

Exclusions reject version ranges and protocol dependencies. See the supported forms in [`lpm config`](/docs/infra/config#exclude-selected-packages-from-the-release-cooldown).
Approved floors can prevent a lower age or broader exclusion.

### Integrity and package verification

| Key | Accepted value | Default | Behavior |
| --- | --- | --- | --- |
| `signatures` | Boolean | `false` | Require valid npm registry signatures for registry packages. |
| `trust-policy` | `"off"` or `"no-downgrade"` | `"off"` | Refuse weaker trusted-publisher or verified provenance evidence than established package history. |
| `integrity` | `"source"` or `"tree"` | `"source"` | Check reused store source identity, or also hash expanded files. |
| `sigstore.verify` | `"deny"`, `"warn"`, `"off"` | `"deny"` | Response to invalid provenance. |
| `sigstore.scope` | `"approved"` or `"all"` | `"approved"` | Verify previously approved identities, or all resolved packages. |
| `sigstore.availability` | `"best-effort"` or `"strict"` | `"best-effort"` | Preserve missing evidence, or fail when attestations are absent or unavailable. |
| `typosquat-guard` | `"default"`, `"on"`, `"off"` | `"default"` | Suspicious direct dependency name checks. The built-in default is disabled. |

```toml
signatures = true
trust-policy = "no-downgrade"
integrity = "tree"
typosquat-guard = "on"

[sigstore]
verify = "deny"
scope = "all"
availability = "strict"
```

`LPM_VERIFY_REGISTRY_SIGNATURES` overrides `signatures`.
`LPM_V2_OBJECT_INTEGRITY` overrides `integrity`.
`LPM_PROVENANCE_ENFORCE` overrides provenance posture, subject to approved floors.
See [Environment variables](/docs/reference/env-vars) for accepted values.

`trust-policy` uses this file. Unknown strings and non-string values fail instead of disabling the policy.
The verified artifact-history floor applies even with provenance warnings, skip flags, or best-effort availability.
Attestation pointers alone do not establish verified history.

A valid explicit typosquat setting takes precedence over the diagnostic environment toggle.
`default` removes the explicit setting through the CLI. It cannot weaken an approved or managed guard without approval.
Use project [typosquat exceptions](/docs/reference/lpm-toml#typosquat-policy) for intentional package names.

## npm firewall policy profile

LPM Firewall checks npm package verdicts. Its hosted service requires an LPM.dev Registry Pro or Org account.
Use [`lpm login`](/docs/infra/login) locally or `LPM_TOKEN` in CI.

```toml
[firewall]
mode = "monitor"

[firewall.npm.policies]
trusted_public_malicious_advisories = "block"
lpm_ai_confirmed_malware = "block"
lpm_ai_agent_control_surface = "warn"
critical_vulnerability = "warn"
lpm_ai_suspicious = "warn"
```

`firewall.mode` accepts `off`, `monitor`, and `enforce`. The default is `off`.
Monitor mode warns and continues. Enforce mode blocks denied packages.
The listed actions are the default profile. Each group accepts `allow`, `warn`, or `block`.
Unknown policy names and invalid actions fail validation.

`LPM_NPM_FIREWALL` can tighten the user mode but cannot weaken it.
`report` is a compatibility alias for `monitor`.
The legacy `static_only_suspicious` group applies only when `lpm_ai_suspicious` is absent.
Configuration commands write canonical names.

Installs read profiles when LPM Firewall is active. `lpm config list` also checks inactive profiles.
See [Firewall for npm](/docs/guides/firewall) for policy meanings, mode aliases, and entitlement behavior.

## Policy extensions

Local extensions supply package verdicts before registry downloads and linking.
Lockfile and offline replay still run these checks.

```toml
[policy.extensions.local-feed]
command = ["/usr/local/bin/lpm-policy-feed", "--deny-list", "/etc/lpm/deny.json"]
mode = "enforce"
on-error = "block"
timeout-ms = 5000
events = ["package.candidate"]
```

| Field | Accepted value | Default |
| --- | --- | --- |
| `enabled` | Native Boolean | `true` |
| `command` | Nonempty string array, at most 64 nonempty arguments | Required when enabled |
| `mode` | `report` or `enforce` | `report` |
| `on-error` | `warn` or `block` | `warn` for report mode, `block` for enforce mode |
| `timeout-ms` | Integer or decimal string from 1 to 120000 | `5000` |
| `events` | Nonempty array containing `package.candidate` | `["package.candidate"]` |

Extensions run in name order.
The executable must be an absolute path or a program from an absolute `PATH` directory.
LPM CLI starts it directly with a restricted environment and exchanges JSON through stdin and stdout.
Relative executables and empty arguments are rejected.

Unknown extension fields fail even when `enabled = false`.
Disabled extensions can omit `command` and skip the other known-field checks.
`warn` aliases report mode. `deny` and `block` alias enforce mode.
For `on-error`, `report` aliases warn, while `deny` and `enforce` alias block.

Extensions use this user file. They are separate from signed machine approvals and managed policy.
Active extensions reject direct remote tarball dependencies before download.
See [`lpm policy`](/docs/infra/policy) for the request and response formats, output bounds, and troubleshooting.

```bash
lpm policy list --json
lpm policy test local-feed --package react@19.0.0 --json
```

### Tunnel relay

```toml
[tunnel]
relay-url = "wss://relay.lpm.fyi/connect"
```

A nonblank `LPM_TUNNEL_RELAY` value overrides the saved URL.
The endpoint must use `wss://`, or `ws://` on loopback.
An invalid selected endpoint produces a warning and uses the default shown above.
An invalid environment endpoint does not retry the saved URL.
See [`lpm tunnel`](/docs/infra/tunnel) for relay trust and connection recovery.

## String coercion

Native TOML types are recommended.
Generic configuration writes can store strings. Readers accept specific aliases according to the setting:

| Setting | True strings | False strings |
| --- | --- | --- |
| Ordinary user Boolean settings | `true`, `1`, `yes`, `on`, `enabled` | `false`, `0`, `no`, `off`, `disabled` |
| `save-exact`, `sandbox.allow-degraded` | `true`, `1`, `yes` | `false`, `0`, `no` |

These strings are exact and case-sensitive unless the setting documents another parser.
Automatic skill installation also accepts whitespace and case variations.
`typosquat-guard` accepts string aliases with whitespace and case variations, but not native TOML Booleans.

Unknown top-level keys usually have no effect. Firewall policy names and extension fields are exceptions.
Invalid-value behavior also differs:

- Invalid `force-security-floor` or `trust-policy` values fail security-sensitive reads and configuration writes.
- Invalid `sigstore.verify` values fall back to `deny`.
- Unknown string values for `linker`, `sigstore.scope`, and `sigstore.availability` fail. Non-string values act as absent during installation.
- Invalid ordinary Boolean values usually act as absent. Source analysis, Registry insights, and automatic skill settings have stricter readers.
- Invalid user script policy acts as absent. Unknown advisor strings warn and select no advisor.

`lpm config list` checks more fields than an individual command and can reject values that command-specific readers ignore.

## Security-sensitive keys are proposals

A hand edit cannot independently authorize weaker protection.
LPM CLI also checks signed machine approvals, temporary unlocks, and managed policy.
An unauthorized reduction fails with `security_approval_required`. Managed policy can reject it with `security_floor`.

Use [`lpm security`](/docs/infra/security) for temporary exceptions.
Use [`lpm config`](/docs/infra/config) for persistent approved changes.
JSON and non-interactive commands do not display approval prompts.

To remove an active `force-security-floor`, first obtain a global floor-edit grant:

```bash
lpm security unlock floor-edit --global
lpm config unset force-security-floor
```

An active grant also permits `lpm config set force-security-floor false`.
Project grants, expired grants, and default unlock scopes do not authorize this persistent change.
The change does not remove other approved controls or managed policy.
Invalid hand-edited values must be corrected before security-sensitive commands can continue.

## Precedence

There is no universal order across all configuration files.
Use the rules in each setting group. CLI flags can replace values, combine with them, or add list entries.

Global installations use user defaults and supported CLI or environment overrides.
They do not inherit settings from the caller's project manifest.
For example, `trust-policy` remains a user setting, while `integrity` also has an environment override.
See [`lpm global`](/docs/packages/global) for supported global flags.

### Exception — `linker`

The layout selection order is:

1. `lpm install --linker`.
2. User `linker` in this file.
3. Nonempty `LPM_LINKER`.
4. Project `package.json > lpm > linker`.
5. Automatic selection.

Automatic selection uses hoisted layout for single packages and isolated layout for workspaces.
A default install with peer conflicts also switches to isolated layout.
An explicit value disables that automatic switch.
Changing the selected layout invalidates the install state and relinks on the next install.
See [dependency layout](/docs/packages/content-addressable-store) and [`lpm install`](/docs/packages/install).
