title: package.json — "lpm" key
description: Configure dependency layout, peer checks, lifecycle scripts, trust, and version policy in package.json.
---

The `lpm` object in `package.json` holds shared package-management configuration. It works with npm, private registries, and LPM.dev Registry.

```json title="package.json"
{
  "name": "my-app",
  "private": true,
  "lpm": {
    "strictDeps": "strict",
    "strictPeerDependencies": true,
    "scriptPolicy": "deny"
  }
}
```

```bash
lpm install
lpm config list --json
```

Use [`lpm config list`](/docs/infra/config) to inspect effective configuration and its sources. Edit `package.json` to change these shared values.
The generic [`lpm config set`](/docs/infra/config) command writes user configuration instead.

## File scope and precedence

Each project manifest defines its dependencies and package policy. Workspace rules differ by field, as described below.
There is no single precedence order for the whole `lpm` object.

| File | Purpose |
| --- | --- |
| `package.json > lpm` | Dependency layout, resolution policy, lifecycle trust, and sandbox requests. |
| [`lpm.json`](/docs/reference/lpm-json) | Runtimes, development services, environments, tasks, and publishing. |
| [`lpm.toml`](/docs/reference/lpm-toml) | Project defaults for save policy, workspace execution, and related CLI behavior. |
| [`~/.lpm/config.toml`](/docs/reference/config-toml) | User defaults and machine security policy. |
| [`lpm.config.json`](/docs/reference/lpm-config-json) | Source-package delivery rules for [`lpm add`](/docs/packages/add). |

Security-sensitive project values require authorization if they weaken the approved machine policy.
An install or rebuild then reports `security_approval_required` with a specific recovery command.
See [temporary security unlocks](/docs/infra/security#temporary-unlocks).

Global installs use their own manifest and user configuration. They do not inherit the current project's `lpm` object.
Global trust lives in `~/.lpm/global/trusted-dependencies.json`. See [`lpm global`](/docs/packages/global).

Project and workspace-member manifests have a 16 MiB size limit.
Oversized manifests fail before dependency resolution. See [local configuration limits](/docs/project-setup#local-configuration-size-limits).

## Top-level keys under `"lpm"`

All fields are optional. Defaults below apply when no higher-priority configuration supplies a value.

| Field | Type | Default |
| --- | --- | --- |
| [`linker`](#linker) | `"hoisted"` or `"isolated"` | Automatic. |
| [`strictDeps`](#strictdeps) | `"strict"`, `"warn"`, or `"loose"` | `"warn"`. |
| [`autoInstallPeers`](#autoinstallpeers) | Boolean | `true`. |
| [`strictPeerDependencies`](#strictpeerdependencies) | Boolean | `false`. |
| [`catalogMode`](#catalogmode) | `"manual"`, `"prefer"`, or `"strict"` | `"manual"`. |
| [`cleanupUnusedCatalogs`](#cleanupunusedcatalogs) | Boolean | `false`. |
| [`scriptPolicy`](#scriptpolicy) | `"deny"`, `"allow"`, or `"triage"` | `"deny"`. |
| [`triageAdvisor`](#triageadvisor) | Provider name | `"none"`. |
| [`trustedDependencies`](#trusteddependencies) | Name array or binding object | Empty. |
| [`minimumReleaseAge`](#minimumreleaseage) | Non-negative integer, seconds | `0`. |
| [`minimumReleaseAgePolicy`](#minimumreleaseagepolicy) | `"direct"` or `"strict"` | `"direct"`. |
| [`minimumReleaseAgeExclude`](#minimumreleaseageexclude) | Selector array | Empty. |
| [`engineStrict`](#enginestrict) | Boolean | `true`. |
| [`overrides`](#overrides) | Selector-to-range object | Empty. |
| [`patchedDependencies`](#patcheddependencies) | Package-to-patch object | Empty. |
| [`peerDependencyRules`](#peerdependencyrules) | Peer-rule object | Empty. |
| [`scripts`](#the-lpmscripts-block) | Lifecycle and sandbox configuration | See field table. |
| [`source`](#source) | Relative path string | Automatic source-file selection. |

### `linker`

```json
{ "lpm": { "linker": "isolated" } }
```

| Value | Layout |
| --- | --- |
| `"isolated"` | Each package sees its declared dependencies through package-local links. |
| `"hoisted"` | Root direct dependencies appear in project `node_modules`. Package-local dependency links use shared store entries. |

Single-package projects default to `hoisted`. Workspace projects default to `isolated`.
The hoisted layout does not flatten every transitive dependency into the project root.

A default-hoisted install with incompatible peer requirements switches to `isolated` and records that decision in `lpm.lock`.
An explicit linker value disables this automatic switch.

Precedence: `--linker` → user `linker` → `LPM_LINKER` → project `lpm.linker` → automatic default.
Unknown values fail installation.

```bash
lpm install --linker isolated
```

See [dependency layout](/docs/packages/dependency-graph) and [`lpm install`](/docs/packages/install).

### `strictDeps`

```json
{ "lpm": { "strictDeps": "strict" } }
```

This field controls source-import checks for the manifest that the install uses.
It does not change the `node_modules` layout.

| Value | Behavior |
| --- | --- |
| `"strict"` | Fail on undeclared package imports or an incomplete source scan. |
| `"warn"` | Show advisory warnings after a full online install in human-readable mode. |
| `"loose"` | Skip these import checks. |

Strict checks run before dependency installation, including unchanged, offline, and JSON installs.
Source edits trigger another check even when the manifest and lockfile remain unchanged. Unknown mode strings fail installation.

The check scans JavaScript and TypeScript files in `src`, `app`, `pages`, `components`, and `lib`.
If none of these directories exists, it scans the project directory.
It skips nested packages, declaration files, generated directories, and symlinked files.

Declarations in `dependencies`, `devDependencies`, `optionalDependencies`, and `peerDependencies` satisfy the check.
Node built-ins, package self-imports, relative imports, and recognized local aliases do not require another dependency declaration.
Aliases can come from TypeScript paths, `baseUrl`, or `lpm.config.json > importAlias`.

After a full online install, strict mode also warns about imports whose packages remain uninstalled.
This advisory appears only in human-readable output.

This static check does not prove that every import resolves at runtime. It cannot resolve a dynamically constructed package name.
If a strict check fails, correct the import or declare the dependency:

```bash
lpm install missing-package
```

### `autoInstallPeers`

```json
{ "lpm": { "autoInstallPeers": false } }
```

By default, LPM CLI installs missing non-optional peers automatically. Optional peers never trigger automatic installation.
With `false`, missing peers remain diagnostics that you can resolve with explicit dependencies.

Precedence: project `autoInstallPeers` → user `auto-install-peers` → `true`.

### `strictPeerDependencies`

```json
{ "lpm": { "strictPeerDependencies": true } }
```

With `true`, missing required peers, incompatible peer versions, and peer conflicts fail installation.
With `false`, these conditions produce warnings. An absent optional peer does not fail the check.

Precedence: `--strict-peer-dependencies` or `--no-strict-peer-dependencies` → project value → user `strict-peer-dependencies` → `false`.

```bash
lpm install --no-strict-peer-dependencies
```

### `catalogMode`

```json
{ "lpm": { "catalogMode": "prefer" } }
```

This field controls how [`lpm install <pkg>`](/docs/packages/install) saves registry dependencies against the root default catalog.

| Value | Save behavior |
| --- | --- |
| `"manual"` | Save the normal range or the explicit version specification. |
| `"prefer"` | Save `catalog:` when the default catalog matches. Otherwise, warn and save the direct specification. |
| `"strict"` | Require a matching default-catalog entry before the manifest change can succeed. |

Automatic catalog modes take priority over explicit registry versions, save flags, and existing registry ranges.
They preserve workspace links, local paths, aliases, Git sources, and tarball URLs.

An explicit catalog request applies to one install:

```bash
lpm install react --catalog
lpm install vitest --catalog=testing
```

Hand-written `catalog:` and `catalog:<name>` dependencies resolve in every mode.
See [`lpm catalog`](/docs/packages/catalog) and [save policy](/docs/packages/save-policy).

### `cleanupUnusedCatalogs`

```json
{ "lpm": { "cleanupUnusedCatalogs": true } }
```

After a successful install, remove catalog entries with no root or workspace-member reference.
LPM CLI checks all four dependency sections, including peers and optional dependencies.

For pnpm workspaces, `pnpm-workspace.yaml > cleanupUnusedCatalogs` enables the same behavior.
An explicit `package.json > lpm.cleanupUnusedCatalogs` value takes priority.

### `scriptPolicy`

```json
{ "lpm": { "scriptPolicy": "deny" } }
```

This field controls dependency lifecycle scripts for [`lpm install`](/docs/packages/install) and [`lpm rebuild`](/docs/packages/rebuild).
Root-project lifecycle scripts have a separate [execution contract](/docs/packages/install#lifecycle-scripts).

| Value | Dependency behavior |
| --- | --- |
| `"deny"` | Block scripts without individual trust or approval. |
| `"allow"` | Permit all dependency lifecycle scripts and request automatic execution during install. |
| `"triage"` | Evaluate scripts with security analysis, trust, provenance, and an optional advisor. |

Precedence: CLI policy flag → project `scriptPolicy` → user `script-policy` → `deny`, subject to approved security policy.
The user `force-security-floor` setting can suppress weaker project values and CLI overrides.

Triage approval makes a package eligible to run. An install starts automatic execution if any of these conditions applies:

- `--auto-build` is set.
- `scripts.autoBuild` is `true`.
- All packages with unbuilt scripts are trusted.
- The effective policy is `allow`.

The `scripts.denyAll` switch blocks execution in every policy mode.
Invalid policy strings and wrongly typed lifecycle controls fail before execution, including under `--json`.
For example, `"denyAll": "true"` is invalid. Use the Boolean `true`.

### `triageAdvisor`

```json
{ "lpm": { "scriptPolicy": "triage", "triageAdvisor": "codex" } }
```

| Value | Provider |
| --- | --- |
| `"none"` | No advisor. The other security checks still apply. |
| `"claude-cli"` | Claude CLI. |
| `"codex"` | Codex CLI. |
| `"ollama"` | A local Ollama model. |

The advisor is active only under the `triage` policy.
Precedence: `--advisor` → project `triageAdvisor` → user `triage-advisor` → `none`.
An unknown or unavailable provider produces a warning, and installation continues without the advisor.

Advisor verdicts can use a local cache. A cached verdict does not create a persistent `trustedDependencies` entry.
Execution approval belongs to the current install. Packages that do not run remain available for review.
Use [`lpm approve-scripts`](/docs/packages/approve-scripts) for durable trust.

See [the optional advisor](/docs/packages/security-audit#optional-llm-advisor).

### `trustedDependencies`

The legacy array grants trust by package name:

```json
{ "lpm": { "trustedDependencies": ["esbuild", "sharp"] } }
```

The binding form records the package version, source integrity, and lifecycle-script hash:

```json
{
  "lpm": {
    "trustedDependencies": {
      "esbuild@0.25.1": {
        "integrity": "sha512-...",
        "scriptHash": "sha256-..."
      }
    }
  }
}
```

A changed binding requires another review. Trust does not bypass sandbox-capability approval or `scripts.denyAll`.
Manage bindings with [`lpm approve-scripts`](/docs/packages/approve-scripts) and inspect changes with [`lpm trust diff`](/docs/packages/trust).

A top-level `trustedDependencies` field outside `lpm` does not grant lifecycle trust.

### `minimumReleaseAge`

```json
{ "lpm": { "minimumReleaseAge": 86400 } }
```

The cooldown delays installation of new package versions. The unit is seconds. `0` disables the cooldown.
A range can select an older eligible version. An exact pin fails during its cooldown.
The selected version does not exceed the current `dist-tags.latest` target in semantic-version order.

Precedence: CLI → project value → user `minimum-release-age-secs` → `0`, subject to approved security policy.

For an authorized one-run bypass:

```bash
lpm install --allow-new
```

### `minimumReleaseAgePolicy`

```json
{ "lpm": { "minimumReleaseAgePolicy": "strict" } }
```

| Value | Scope |
| --- | --- |
| `"direct"` | Direct dependencies. |
| `"strict"` | Direct and transitive dependencies, including lockfile replay. |

Strict replay checks use saved publication timestamps when available.
Precedence: project value → user `release-age-policy` → `direct`, subject to approved security policy.

### `minimumReleaseAgeExclude`

```json
{ "lpm": { "minimumReleaseAgeExclude": ["react", "@company/*", "react@19.1.0"] } }
```

Accepted selectors are package names, scope wildcards, and exact package versions.
Ranges such as `react@^19` and protocol values such as `npm:react` are invalid.
Aliases match their canonical package name.

CLI, project, and user lists combine in that order. Duplicate selectors appear once.
Manage the project list with [`lpm trust release-age-exclude`](/docs/packages/trust#lpm-trust-release-age-exclude).

### `engineStrict`

```json
{ "lpm": { "engineStrict": true } }
```

The workspace-root value controls engine checks. Member values do not replace it.
LPM CLI checks root `engines.lpm` and `engines.node`, plus selected dependencies' Node requirements during installation.

A required dependency with an incompatible Node requirement fails installation.
A package reachable only through optional dependencies is omitted instead.
With `false`, incompatible dependencies remain installed and human-readable output shows warnings.

Precedence: `--no-engine-strict` → root project value → user `engine-strict` → `true`.
See [Node version pinning](/docs/dev/node-version-pinning).

### `overrides`

```json
{
  "lpm": {
    "overrides": {
      "lodash": "^4.17.21",
      "react@<18": "18.0.0",
      "baz>foo@1": "2.0.0"
    }
  }
}
```

| Selector | Matches |
| --- | --- |
| `foo` | Every instance of `foo`. |
| `foo@<1.0.0` | Natural selections in that range. |
| `baz>foo` | `foo` dependencies of `baz`. |
| `baz>foo@1` | Matching `foo` versions reached through `baz`. |

The target replaces the matching consumer's declared range.
An exact target pins one version. A range selects the newest eligible version in that range.
Security and platform checks still apply.

Root entries apply to every workspace member. Member entries extend the same field, with member values winning on duplicate selectors.
Across fields, precedence is `lpm.overrides` → top-level `overrides` → `resolutions`.

Targets must be strings. Nested npm override objects produce warnings and do not apply.
Multi-segment selectors such as `a>b>c` fail installation.

Plain and unqualified parent selectors can rescue a range with no available version.
Range-qualified selectors require a natural candidate. They do not match a replacement from another override.

If override selection fails, LPM CLI warns and retains the natural selection.
A required dependency fails if neither selection is available. Later engine checks can also fail or omit a selected package.

Summaries include overrides that change a version. A rescued dependency shows `unresolved` in text and `from_version: null` in JSON.
See [resolver overrides](/docs/packages/resolver#overrides-and-aliases).

### `patchedDependencies`

```json
{
  "lpm": {
    "patchedDependencies": {
      "lodash@4.17.21": {
        "path": "patches/lodash@4.17.21.patch",
        "originalIntegrity": "sha512-..."
      }
    }
  }
}
```

Each key uses an exact package version. `path` is relative to the manifest that declares it.
[`lpm patch`](/docs/packages/patch) and [`lpm patch-commit`](/docs/packages/patch) create these entries.

Patches apply after dependency linking and before lifecycle scripts.
Installs check the patch checksum from `lpm.lock` and the selected package's source integrity. A mismatch stops installation.
These checks do not detect an upstream republish until an install selects the changed source.

Deliberately omitted dependencies retain their patch registrations. A registration absent from the dependency graph produces an error.
Patches cannot change dependency resolution or repair a peer conflict that prevents installation.

### `peerDependencyRules`

```json
{
  "lpm": {
    "peerDependencyRules": {
      "ignoreMissing": ["fsevents"],
      "allowedVersions": { "card>react": "18 || 19" },
      "allowAny": ["@babel/*"]
    }
  }
}
```

| Field | Type | Effect |
| --- | --- | --- |
| `ignoreMissing` | Name or glob array | Suppress matching missing-peer diagnostics. |
| `allowedVersions` | Selector-to-range object | Accept this range in addition to the peer's declared range. |
| `allowAny` | Name or glob array | Accept any installed version. Missing-peer diagnostics still apply. |

#### `allowedVersions` selector grammar

| Selector | Matches |
| --- | --- |
| `react` | The peer named `react` for any consumer. |
| `@scope/foo` | A scoped peer for any consumer. |
| `foo>react` | The `react` peer of `foo`. |
| `foo@^2>react` | The `react` peer of a matching `foo` version. |
| `@scope/foo@^2>react` | The same rule with a scoped consumer. |

Multi-segment paths, standalone peer-version qualifiers such as `foo@2`, and globs are invalid in `allowedVersions`.
Invalid selectors and ranges fail installation.
[`lpm migrate`](/docs/packages/migrate) translates supported pnpm peer rules and checks the same selector grammar.
[`lpm doctor --json`](/docs/infra/doctor) reports later pnpm/LPM CLI rule differences as `pnpm_peer_rules_drift`.

## The `lpm.scripts` block

```json
{
  "lpm": {
    "scripts": {
      "autoBuild": true,
      "denyAll": false,
      "trustedScopes": [],
      "passEnv": [],
      "readProject": "narrow",
      "sandboxWriteDirs": ["build/"]
    }
  }
}
```

These fields control dependency lifecycle scripts and their requested sandbox access.

| Field | Type and default | Effect |
| --- | --- | --- |
| `autoBuild` | Boolean, `false` | Request automatic execution of trusted scripts. A lifecycle failure fails installation. |
| `denyAll` | Boolean, `false` | Block every dependency lifecycle script, including trusted scripts. |
| `trustedScopes` | String array, empty | Trust every package version and script in the listed lowercase npm scopes. |
| `passEnv` | String array, empty | Request additional environment variables. Reserved runtime variables are invalid. |
| `readProject` | `"narrow"` or `"full"`, `"narrow"` | Narrow reads permit dependency directories and build metadata. Full reads include project secrets. |
| `sandboxLimits` | Object, empty | Request resource limits with non-negative integer values. |
| `sandboxWriteDirs` | String array, empty | Request additional writable directories. |
| `sandboxReadAllow` | String array, empty | Request read access to individual files inside the project. |

`sandboxLimits` accepts `RLIMIT_AS`, `RLIMIT_NPROC`, `RLIMIT_NOFILE`, and `RLIMIT_CPU`.
Limits outside the approved baseline require review. Raw user-configured limits do not grant that authority.

Relative write directories stay inside the canonical project root.
External absolute paths require a covering user `max-sandbox-write-roots` entry and approval.
Dangerous roots remain forbidden. Symlinks, junctions, and reparse points below an authorized root are rejected.
The project root itself can be a symlink to its canonical directory.

`sandboxReadAllow` combines with user `script-read-allow` entries.
Directories, symlinks, and paths outside the project are invalid.
Changes to requested access require another approval through [`lpm approve-scripts`](/docs/packages/approve-scripts).

Manage scope trust with [`lpm trust lifecycle-scope`](/docs/packages/trust#lpm-trust-lifecycle-scope).
An added scope requires signed `trust-scope-widen` authorization. Removal also removes that local authorization.
For individual packages, prefer [version and integrity bindings](#trusteddependencies).

### `source`

```json
{ "lpm": { "source": "src/components" } }
```

This legacy field selects a file or directory for source-package delivery with [`lpm add`](/docs/packages/add).
It applies when `lpm.config.json` does not provide `files` rules.
The path must stay inside the extracted package. Directory contents keep paths relative to that directory.
For new packages, use [`lpm.config.json`](/docs/reference/lpm-config-json).

## Related top-level fields

These fields belong directly in `package.json`, outside `lpm`.

### `workspaces`

```json
{ "workspaces": ["packages/*", "apps/*"] }
```

The object form is also accepted:

```json
{ "workspaces": { "packages": ["packages/*"] } }
```

See [workspaces](/docs/packages/workspaces).

### `engines`

```json
{ "engines": { "node": ">=22.0.0", "lpm": ">=0.78.0" } }
```

`engines.node` checks compatibility. It does not select or install Node.
Runtime selection uses `lpm.json > runtime.node`, `.nvmrc`, or `.node-version`, then the Node on `PATH`.
A missing required runtime produces an error with a selection hint.

LPM CLI also checks the root `engines.lpm` value against its own version.
Other manager keys, including `npm`, `pnpm`, `yarn`, and `bun`, produce warnings and are not enforced.
Use `lpm.json > runtime.bun` to select a managed Bun runtime.

### `overrides` / `resolutions`

These compatibility fields use the supported [override rules](#overrides).
Root entries apply to workspace members, and same-field member values take priority.

### `scripts`, `bin`, `dependencies`, `devDependencies`, `peerDependencies`, `optionalDependencies`

LPM CLI reads these standard npm fields for tasks, executable links, and dependency resolution.
See [npm compatibility](/docs/packages/npm-compatibility) for supported behavior.

### `catalogs`

```json
{
  "catalogs": {
    "default": { "react": "^19.0.0" },
    "testing": { "vitest": "^3.0.0" }
  }
}
```

Members reference these ranges with `catalog:` or `catalog:<name>`.
LPM CLI also reads `pnpm-workspace.yaml > catalog` and `catalogs`.
On duplicate entries, root `package.json > catalogs` takes priority.

Catalog values must be package ranges. A catalog cannot reference another catalog.
See [`lpm catalog`](/docs/packages/catalog).

## Validation and recovery

```bash
lpm doctor --all --json
lpm config list --json
lpm install --json
```

[`lpm doctor`](/docs/infra/doctor) reports configuration and compatibility problems.
The command that consumes a field performs its behavior-specific checks.
Invalid lifecycle controls fail instead of inheriting a more permissive policy.

If a strict import check fails, add the missing declaration or correct the import.
If a security approval is required, review the requested scope before you use the reported unlock command.
If a peer check fails, correct the dependency ranges or define a specific peer rule.
