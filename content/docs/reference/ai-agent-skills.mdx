**Agent skills** are Markdown instructions that help an AI agent use a package, workflow, or project correctly. The LPM CLI supports two distinct kinds under one `lpm skills` command family.

## Package-published skills

Package-published skills are a permanent LPM.dev Registry feature. Package authors publish them with an `@lpm.dev/*` package, and the LPM.dev publishing and registry flow validates their content.

Installing a direct package extracts its published skills automatically:

```bash
lpm install @lpm.dev/owner.package
```

They are materialized as package-owned files:

```text
my-project/
└── .lpm/
    └── skills/
        └── owner.package/
            ├── usage.md
            └── gotchas.md
```

Automatic reconciliation is enabled by default. Use `--no-skills` with [`lpm install`](/docs/packages/install), [`lpm add`](/docs/packages/add), or `lpm ci` to opt out for one invocation. To make that preference persistent, run:

```bash
lpm config lpm-skills --set false
```

Use `--skills` on those install surfaces to override a disabled setting for one run. The precedence is `--skills` / `--no-skills`, then `auto-install-lpm-skills`, then the legacy `noSkills` fallback, then the enabled default.

The setting controls only automatic fetching and reconciliation. It does not delete existing `.lpm/skills/` content and does not affect explicit commands. To fetch one package's published set explicitly, use:

```bash
lpm skills add @lpm.dev/owner.package
```

Package-published skills are versioned package knowledge. They stay in `.lpm/skills/<package>/`; the LPM CLI does not convert them into standalone managed skills, create agent links, or modify editor configuration. Point your agent at that directory when you want it to apply the package author's current guidance:

```text
Read .lpm/skills/owner.package/ before changing code that uses @lpm.dev/owner.package.
```

When automatic installation is enabled, installing or upgrading a package reconciles its directory to the exact published set, removing guidance that the new package version no longer ships. Uninstalling the package removes its package-owned skill directory. If automatic installation is disabled, use `lpm skills clean` when you also want to remove previously materialized package skills.

## Standalone skills

The same command manages public or local standard `SKILL.md` directories. A source may be a GitHub shorthand, an HTTPS GitHub repository or tree URL, or a local path.

```bash
lpm skills add vercel-labs/skills --skill find-skills
lpm skills add vercel-labs/agent-skills
lpm skills add https://github.com/vercel-labs/agent-skills --skill web-design-guidelines
lpm skills add ./team-skills --skill release-notes --agent codex --project
```

In a terminal, `lpm skills add` opens a wizard to choose the source, skills, scope, compatible targets, and confirmation. For CI and scripts, provide flags and `--yes` after reviewing `--dry-run`.

`lpm skills install` is accepted as a compatibility alias for `lpm skills add`; use `add` in new scripts.

Standalone skills are stored in an LPM-managed canonical location, then linked by default (or copied with `--copy`) to selected agent directories:

| Target | Project directory |
| --- | --- |
| Codex | `.agents/skills/<skill>/` |
| Claude Code | `.claude/skills/<skill>/` |
| Cursor | `.cursor/skills/<skill>/` |

Project-managed content lives in `.lpm/managed-skills/`; global-managed content lives under the LPM home directory. This is separate from package-published `.lpm/skills/` content.

## Source and security boundary

Standalone GitHub sources must use HTTPS. The LPM CLI resolves branches—including names containing `/`—tags, and commit refs to an immutable commit before downloading from `codeload.github.com`. `GH_TOKEN` or `GITHUB_TOKEN` is used only for authenticated `api.github.com` requests and is not forwarded to codeload. The source boundary limits downloads to 20 MB, expanded content to 64 MB, regular files to 1 MB, 500 archive entries, and 12 directory levels. Traversal is always rejected; symlinks, hard links, special entries, and oversized files reject a selected skill without making unrelated repository fixtures block a valid subpath.

Before installation, it scans every selected skill for prompt injection, secret access or exfiltration, shell-download execution, and destructive filesystem instructions. Findings have stable rule IDs and one of two severities:

| Severity | Effect |
| --- | --- |
| `warning` | Shown in the plan. Installation can continue after explicit confirmation. |
| `block` | Installation stops before managed storage or agent targets are written. |

`lpm skills view` reports estimated context size, security findings, and an agent-target health matrix. `lpm skills dashboard` presents the same unified inventory in an authenticated local browser page, with preview-and-apply controls for managed skills. Its agent labels represent configured targets, not observed runtime usage, and its context figures are estimates rather than actual session or billing tokens. `lpm skills update --dry-run` shows a bounded content diff and computes new findings by identity—rule, severity, file, and line—rather than comparing counts. Binary auxiliary files are preserved and represented by their SHA-256 digest in update diffs instead of being interpreted as text.

## Inventory and maintenance

```bash
lpm skills list                         # package-published, managed, and external inventory
lpm skills view release-notes           # source, context, security, and target state
lpm skills dashboard --global           # authenticated local inventory and management UI
lpm skills doctor                       # managed-link health
lpm skills update release-notes         # re-resolve and refresh a managed source
lpm skills disable release-notes        # remove target links while retaining managed content
lpm skills enable release-notes         # restore recorded target links
lpm skills remove release-notes         # remove managed content and target links
lpm skills prune --dry-run              # preview stale-link and state cleanup
lpm skills validate                     # validate package-published .lpm/skills content
lpm skills clean                        # remove package-published .lpm/skills content
```

`list` and `view` distinguish three inventory categories:

- `package`: package-published LPM.dev skills in `.lpm/skills/`.
- `managed`: standalone skills explicitly added through `lpm skills add`.
- `external`: pre-existing skills discovered in agent directories but not managed by LPM CLI.

`clean` only removes package-published `.lpm/skills/` content. It does not remove standalone managed content or agent links. Re-run `lpm install` to repopulate package-published skills after a clean.

Project-managed target paths and links are relative to the project, so moving the project directory keeps healthy links intact. `doctor` distinguishes missing canonical content, missing targets, ownership mismatches, disabled targets, and broken external symlinks. `prune --dry-run` shows the exact target and state-file paths before cleanup.

JSON mode always emits one envelope, including no-op operations. Unified inventory includes total and per-category counts. For example, `skills validate`, `skills clean`, and `skills prune --yes` report successful zero-count results when there is nothing to change.
