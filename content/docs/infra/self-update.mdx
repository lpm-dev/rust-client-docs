---
title: lpm self-update
description: "Update LPM CLI on the stable or nightly release channel."
---

Use `lpm self-update` to update LPM CLI or switch release channels. The command detects the installation method and uses its update process.

```bash
lpm self-update [OPTIONS]
lpm self-update [--channel <stable|nightly>] [--refresh] [--json]
```

## Quickstart

Update LPM CLI on its current release channel:

```bash
lpm self-update
```

## Choose a task

| Task | Command |
| --- | --- |
| Update on the installed channel | `lpm self-update` |
| Switch to nightly | `lpm self-update --channel nightly` |
| Switch to stable | `lpm self-update --channel stable` |
| Ignore the lookup cache and retry now | `lpm self-update --refresh` |
| Get a structured result | `lpm self-update --json` |

This command manages the LPM CLI installation on your computer. `lpm.json` does not control or run CLI updates.

## Release channels

Without `--channel`, LPM CLI uses the channel of the installed version. Stable versions continue on stable, and nightly versions continue on nightly.

A version such as `0.71.0-nightly.20260728.42.d82ceea` selects nightly. A version without the `nightly` prerelease identifier selects stable.

An explicit `--channel` value changes the channel. A switch from nightly to stable can install a lower semantic version.

| Installation method | Stable | Nightly |
| --- | --- | --- |
| npm, pnpm, Bun, Yarn, Volta | Supported | Supported |
| Standalone | Supported | Supported |
| Homebrew | Supported | Not supported |
| Cargo | Supported | Not supported |

Homebrew and Cargo installations return an error for `--channel nightly`. Use a supported registry package manager or a standalone installation for nightly releases.

## How the update runs

LPM CLI identifies the installation method from the current executable. Normal output and JSON output have different update behavior.

| Installation method | Normal output | With `--json` |
| --- | --- | --- |
| npm, pnpm, Bun, Yarn, Volta | Runs a version-pinned global package update | Returns the command and does not run it |
| Homebrew | Runs `brew upgrade lpm` | Returns the command and does not run it |
| Cargo | Verifies the release, then installs its source commit | Verifies the release and returns the commit-pinned command |
| Standalone | Verifies and replaces the binary | Verifies and replaces the binary |

> **CAUTION:** `--json` is not a universal preview. It applies the update for a standalone installation.

On the same channel, a current or newer installed version needs no update. An explicit channel switch can install a lower version.

## Recipes

### Update on the installed channel

```bash
lpm self-update
```

Use this command for normal updates. Stable and nightly installations remain on their current channels.

### Switch to nightly

```bash
lpm self-update --channel nightly
```

Use nightly for early access to unreleased changes. Nightly releases can change more frequently than stable releases.

### Return to stable

```bash
lpm self-update --channel stable
```

This command can replace a newer nightly version with a lower stable version. The channel change is intentional.

### Retry a version lookup

```bash
lpm self-update --refresh
```

Use `--refresh` after a lookup failure, or after a release appears during the 10-minute cache period.

The flag also bypasses the one-hour cooldown after a failed lookup. It does not change the verification or installation process.

### Get an external update plan

> **CAUTION:** Use this recipe for an installation owned by an external package manager. A standalone installation applies the update.

```bash
lpm self-update --json
```

For an external installation method, read `install_method`, `update_shell`, and `update_command`. Run the returned command in the specified shell.

For programmatic execution, use `update_program` with the `update_args` array. The plan uses an absolute manager path and preserves names such as `cargo`.

Plan creation checks the current launcher and its owning manager. It does not reserve the installation for a later command.

There is no universal dry-run flag for `lpm self-update`.

### Run the update command manually

| Installation method | Manual command |
| --- | --- |
| Homebrew | `brew upgrade lpm` |
| npm | `npm install -g @lpm-registry/cli@<version>` |
| pnpm | `pnpm add --global @lpm-registry/cli@<version>` |
| Bun | `bun add --global @lpm-registry/cli@<version>` |
| Yarn | `yarn global add @lpm-registry/cli@<version>` |
| Volta | `volta install @lpm-registry/cli@<version>` |
| Cargo | `cargo install --git https://github.com/lpm-dev/rust-client --rev <verified-source-commit> lpm-cli --force --locked` |
| Standalone | `lpm self-update` |

For npm, you can also follow a channel tag:

```bash
npm install -g @lpm-registry/cli@latest   # newest stable
npm install -g @lpm-registry/cli@nightly  # newest nightly
```

## Cargo source verification

For a Cargo installation, LPM CLI verifies the signed release manifest before it starts Cargo.

The signature identifies the exact release workflow, Git reference, and source commit. LPM CLI then uses that commit with `cargo install --rev`.

The `--locked` flag makes Cargo use the dependency versions in the release lockfile. A moved Git tag cannot change the selected source commit.

`lpm self-update --json` applies the same verification. It returns the verified `--rev` command without running Cargo.

## Update source trust

LPM CLI uses a different trust model for each installation method.

| Installation method | Trust source |
| --- | --- |
| Standalone | The signed release manifest, release identity, source commit, and asset checksum |
| Cargo | The signed release source commit and the locked dependency versions |
| npm, pnpm, Bun, Yarn, and Volta | The configured registry or mirror and package manager verification |
| Homebrew | The configured Homebrew repository and formula |

LPM CLI resolves each external manager from a filtered `PATH`. The manager must use an absolute, non-project path with trusted ownership.

The filter removes project paths, relative paths, `node_modules/.bin` directories, and directories without trusted write permissions. LPM CLI also excludes directories with project-owned or untrusted executable targets.

These rules protect interpreter and helper lookup. Trusted directory aliases resolve to their checked targets. Helper symlink routes must also have trusted write permissions.

On Windows, helper entries that are symbolic links or other reparse points cause LPM CLI to exclude their directory. Ordinary executable files and command shims remain supported.

If a manager or interpreter becomes unavailable, use a trusted global installation and retry. Do not add a shared-writable directory to bypass this check.

LPM CLI verifies the manager file before it runs the update. It also verifies the installed LPM CLI version after the update.

These checks do not add independent artifact attestation to registry managers or Homebrew. Their configured repositories remain part of the trust boundary.

Cargo ownership detection reads the local Cargo install metadata. Stale metadata does not prove the build provenance of the current executable.

LPM CLI rejects intermediate configuration symlinks. It accepts manager symlinks only when their paths and targets pass the same trust checks.

For manager ownership detection, `XDG_CONFIG_HOME` must resolve inside the account home. LPM CLI ignores an external configuration root.

## Version lookup and cache

LPM CLI reads the npm `latest` or `nightly` tag first. If that lookup fails, it uses the corresponding GitHub Releases data.

Successful `lpm self-update` lookups remain cached for 10 minutes. Stable and nightly use separate cache state in `~/.lpm/update-check.json`. This file is in your OS account's home directory, whatever [`LPM_HOME`](/docs/reference/env-vars#filesystem-layout) names.

A failed lookup starts a one-hour cooldown for that channel. A later successful lookup, including a not-modified response, clears that failure state. During the cooldown, the command returns the previous error state without a network request.

Use `--refresh` to bypass the successful-result cache and the failure cooldown.

## Background update notices

Normal LPM CLI commands can print a cached update notice after their command output. JSON commands do not print this notice.

LPM CLI refreshes the update information in a detached process. The command does not wait for this network request.

After a successful background lookup, LPM CLI waits 24 hours before another lookup. A failed lookup has a one-hour cooldown.
A background lookup doesn't block `lpm self-update`: you can run it right after the notice appears.

Disable background lookups and cached update notices for a command with this environment variable:

```bash
LPM_NO_UPDATE_CHECK=1 lpm install
```

`LPM_NO_UPDATE_CHECK` does not disable an explicit `lpm self-update`.

## Standalone update verification

For a standalone installation, LPM CLI downloads the release files and completes these steps before it replaces the binary:

1. It verifies that the signed manifest comes from the expected LPM CLI release workflow.
2. It verifies that the release workflow ran from an accepted Git reference, and that the signing certificate was issued to that run.
3. It verifies that the signed source commit matches the requested version.
4. It verifies that the signing time matches the GitHub release time. The signing time is when the transparency log recorded the signature. For a release logged to Rekor v2, which records no time, it is the time an RFC 3161 timestamp authority signed for the signature.
5. It verifies the checksum of the manifest.
6. It verifies the downloaded release asset against the manifest.
7. It runs the new binary and checks that it reports the requested version.

If any verification step fails, LPM CLI refuses the update and retains the current binary.

### Release signing identity

The release workflow runs only from the `main` branch, so stable and nightly releases are signed from `refs/heads/main`. Stable releases 0.75.0 through 0.76.5 were signed from their version tag, such as `refs/tags/v0.76.5`. LPM CLI accepts a tag signature for that version only, and only up to 0.76.5. It refuses a signature from any other branch or tag.

Sigstore issues the signing certificate for one GitHub Actions run, and records that run's repository, Git reference, commit, and starting event in it. LPM CLI requires a GitHub-hosted run of `lpm-dev/rust-client`, at the signed reference and the signed source commit.

A `main` signature does not name a version, so LPM CLI binds the signed source commit to the requested version:

| Release | Binding |
| --- | --- |
| Nightly | The version ends with the first seven characters of the signed commit. The run was scheduled or started by hand. |
| Stable, signed from `main` | The GitHub release points at the signed commit, and the run was started by hand. |
| Stable, signed from its tag | The signed tag names the version, and a push of that tag started the run. |

On Linux and Windows, the updater attempts to copy the current binary to `<binary>.previous`. This backup is best-effort and can be absent.
On Windows, a running binary can't be deleted, so the updater moves it aside as `<binary>.old.<pid>`. The next update removes those copies once nothing runs them.

On macOS, the updater replaces the app bundle and its command links. It keeps temporary rollback copies during replacement and removes them after success.

If macOS replacement or final verification fails, the updater attempts to restore those copies. It does not retain a permanent `.previous` binary.

### Sigstore trust root

Sigstore rotates the certificate authorities, log keys and timestamp authorities it signs with. LPM CLI holds the Sigstore trust root that was current when it was built. Before it verifies a release, it fetches Sigstore's current trust root from Sigstore's signed update repository at `tuf-repo-cdn.sigstore.dev`. It accepts that trust root only when its signatures trace back to the Sigstore root keys built into LPM CLI. A key Sigstore added after the build then verifies, and a key Sigstore retired is refused.

If the fetch fails, LPM CLI verifies with the newest trust root it already holds: the one built in, or one fetched on an earlier run. The check never falls below what LPM CLI shipped with. If the release needs a key that trust root lacks, the refusal says that the fetch failed.

LPM CLI caches the fetched trust root in `~/.lpm/cache/metadata/sigstore-trust.json`. It checks the cache against the built-in Sigstore root keys each time it reads it, so a changed cache is ignored. `lpm cache clean metadata` removes it. [`LPM_SIGSTORE_TUF_URL_OVERRIDE`](/docs/reference/env-vars#security-and-recovery-overrides) points LPM CLI at a mirror of the repository, or turns fetching off.

### Supported standalone targets

| Operating system | Architecture |
| --- | --- |
| macOS | ARM64 and x64 |
| Linux with glibc | ARM64 and x64 |
| Linux with musl | x64 |
| Windows | ARM64 and x64 |

There is no standalone Linux ARM64 musl asset. On that platform, [install from source](/docs/installation#from-source-cargo).

### macOS app bundle compatibility

The macOS release asset is a ZIP, such as `lpm-darwin-arm64.zip`. Its attestation records the ZIP checksum, not the extracted executable checksum.

Extraction and each system verification command have a 60-second deadline. Each output stream has a 1 MiB limit. A timeout or oversized response fails the update.

The updater accepts signed app bundles with and without the optional application icon. It still checks required files, code signatures, notarization, and the signing identity. Removing a resource covered by the app signature causes verification to fail.

The updater uses only tools that ship with macOS, so it needs neither Xcode nor the Command Line Tools. It needs no connection to Apple either: `codesign` confirms the notarization from the ticket stapled to the app.

The standalone updater shipped in 0.76.5 cannot read newer app bundles. If it reports an unexpected `Contents/Resources/` entry, rerun the installer once:

```bash
curl -fsSL https://cli.lpm.dev/install | sh
```

To recover onto the latest nightly:

```bash
curl -fsSL https://cli.lpm.dev/install | LPM_INSTALL_CHANNEL=nightly sh
```

The installer preserves saved credentials and configuration. It retains the [installer verification checks](/docs/installation#standalone-installer-macos-linux). Do not disable verification or delete your credentials. For npm and Homebrew installations, use the package manager.

### Upgrade on a Mac without Xcode from 0.76.0 to 0.88.0

`lpm self-update` in 0.76.0 to 0.88.0 checks the notarization ticket with `stapler`, which macOS runs only when Xcode is installed. On a Mac without Xcode, including one with only the Command Line Tools, standalone installations of these versions refuse every update:

```text
✗ Self-update refused
  reason macOS notarization-ticket validation failed with status exit status: 1: xcode-select: error: tool 'stapler' requires Xcode, but active developer directory '/Library/Developer/CommandLineTools' is a command line tools instance
```

Without any developer tools, the reason names `xcrun` or `xcode-select` instead. The release is not tampered. Rerun the installer once:

```bash
curl -fsSL https://cli.lpm.dev/install | sh
```

On the nightly channel, rerun it with `LPM_INSTALL_CHANNEL=nightly`:

```bash
curl -fsSL https://cli.lpm.dev/install | LPM_INSTALL_CHANNEL=nightly sh
```

The installer preserves saved credentials and configuration, and installs a release whose updater needs no developer tools. After this one reinstall, `lpm self-update` works again. npm and Homebrew installations are not affected.

### Upgrade from 0.75.0 to 0.84.0

`lpm self-update` in 0.75.0 to 0.84.0 accepts a stable release only when it is signed from its version tag. Newer stable releases are signed from `main`, so standalone and Cargo installations of these versions refuse them:

```text
✗ Self-update refused
  reason release v0.84.0 has invalid signed provenance: certificate identity must be
  `github:lpm-dev/rust-client` workflow `.github/workflows/release.yml` at `refs/tags/v0.84.0`
```

The release is not tampered. For a standalone installation, rerun the installer once:

```bash
curl -fsSL https://cli.lpm.dev/install | sh
```

The installer preserves saved credentials and configuration. For a Cargo installation, install the new release once from its tag:

```bash
cargo install --git https://github.com/lpm-dev/rust-client --tag v<version> lpm-cli --force --locked
```

After this one reinstall, `lpm self-update` works again. npm, Homebrew, and nightly installations are not affected.

### Recover from a standalone update error

If verification fails, do not replace the current binary manually with the rejected download. Retry later or install a trusted exact version.

On Linux or Windows, if the new binary cannot start, look for `<binary>.previous` beside it. Restore that backup or reinstall an exact release.

On macOS, if recovery fails, reinstall a trusted release with the installer.

On macOS and Linux, when the installer can take over, a refused standalone update names the installer command for the channel you update on. That covers a release this version of LPM CLI doesn't accept, and on macOS an installation outside the installer's app layout. The installer verifies the release itself, installs it in `~/.lpm`, and preserves saved credentials and configuration:

```text
✗ Self-update refused
  reason <why the update was refused>
  hint Reinstall LPM CLI with the official installer, which verifies the release itself and keeps your settings:
    curl -fsSL https://cli.lpm.dev/install | LPM_INSTALL_CHANNEL=stable sh
```

A refusal of the installation directory itself, such as one that other accounts can write to, names no installer, because reinstalling doesn't fix it. Make the directory writable only by your account, then retry.

On Linux, when the release itself fails verification, the command also sets `LPM_INSTALL_REQUIRE_SIGSTORE=1`. Without [cosign](https://docs.sigstore.dev/cosign/system_config/installation/), the installer can't tell who published a release's checksums, so install cosign first; the installer then checks the release's signature itself. On macOS, the installer checks the app's Developer ID signature, so it needs no cosign.

The standalone updater does not provide an automatic rollback command. See [Installation](/docs/installation) for exact-version and source installations.

Do not replace the binary with a raw `curl` or `Invoke-WebRequest` download. Those commands do not apply the verification steps on this page.

## Filesystem and process limits

The update lock prevents concurrent LPM CLI updates on local filesystems. Advisory lock behavior on NFS and SMB depends on the filesystem.

On Unix, the update lock is account-specific. The package manager must coordinate updates across accounts that share one installation.

> **CAUTION:** If the LPM CLI installation is on a shared filesystem, run updates from one host at a time.

A process with the same account permissions can replace parent directories, manager paths, or staged files after the final check.

The updater does not protect against a compromised user account or an administrator. Operating-system access controls provide this protection.

On Windows, trusted write access includes the current account, Administrators, SYSTEM, and TrustedInstaller. LPM CLI accepts an OWNER RIGHTS entry only when it trusts the file or directory owner. LPM CLI rejects reparse points in checked paths.

The Windows installation lock uses a global operating-system name. Another local account can block updates by reserving that name.

Homebrew can use user-owned, group-writable directories. LPM CLI accepts this layout only for directories owned by the current account.

LPM CLI terminates the manager process group after errors and timeouts. On Unix, a child that creates a new session can survive cleanup.

```json
  "channel": "stable",
  "target_channel": "stable",
  "channel_changed": false,
  "duration_ms": 120
}
```

### External update plan

For external package managers, JSON output reports a verified update plan without running it:

```json
{
  "success": true,
  "current": "0.71.0",
  "latest": "0.72.0",
  "up_to_date": false,
  "install_method": "npm",
```

### Refused standalone update

On macOS and Linux, when the installer can take over, the error output of a refused standalone update gives the installer command in `next_steps`:

```json
{
  "schema_version": 1,
  "success": false,
  "error": "self-update refused: <why the update was refused>",
  "error_code": "self_update",
  "next_steps": [
    {
      "description": "Reinstall LPM CLI with the official installer, which verifies the release itself and keeps your settings",
      "command": "curl -fsSL https://cli.lpm.dev/install | LPM_INSTALL_CHANNEL=stable sh"
    }
  ]
}
```

The command names the channel you update on, as in `LPM_INSTALL_CHANNEL=nightly`. On Linux, a release that fails verification gets a command that also sets `LPM_INSTALL_REQUIRE_SIGSTORE=1`, with a description that asks you to install cosign first.

### Common fields

| Field | Type | Meaning |
| --- | --- | --- |
| `success` | Boolean | `true` after version discovery and the action for this output mode succeed |
| `current` | String | Version of the running binary |
| `latest` | String | Latest version found on the target channel |
| `up_to_date` | Boolean | `true` for a current or newer version without a channel change |
| `cache_hit` | Boolean | `true` after the command uses a recent successful lookup |
| `channel` | String | Channel of the current binary |
| `target_channel` | String | Channel selected for this command |
| `channel_changed` | Boolean | `true` for different `target_channel` and `channel` values |
| `duration_ms` | Integer | Elapsed command time in milliseconds |

### Outcome fields

| Field | Type | Meaning |
| --- | --- | --- |
| `install_method` | String | Detected method for an available update |
| `update_command` | String | Shell command for an external update plan |
| `update_shell` | String | `posix` on Unix or `powershell` on Windows |
| `update_program` | String | Absolute path to the verified external manager |
| `update_args` | String array | Arguments for that manager |
| `applied` | Boolean | `false` for an external plan |
| `launcher_verified` | Boolean | Current launcher matches the running installation |
| `manager_target_verified` | Boolean | External manager owns that installation |
| `verified` | Boolean | `true` after an applied standalone update passes all verification steps |
| `attestation` | Object | Verification record for an applied standalone update |

### `attestation` fields

| Field | Type | Meaning |
| --- | --- | --- |
| `publisher` | String or null | Verified publisher from the release signature |
| `workflow_path` | String or null | Verified release-workflow path |
| `workflow_ref` | String or null | Verified workflow reference |
| `integrated_time` | String | Signing time in RFC 3339 format: when the transparency log recorded the signature, or for a release logged to Rekor v2, when a timestamp authority signed for it |
| `log_index` | Integer | Entry index in the transparency log |
| `log_id` | String | Identifier of the transparency log |
| `leaf_cert_sha256` | String | SHA-256 digest of the signing certificate |
| `manifest_sha256` | String | SHA-256 digest of the signed manifest |
| `asset_sha256` | String | SHA-256 digest of the downloaded asset: a ZIP on macOS or a binary elsewhere |
| `asset_name` | String | Release asset selected for the current platform |
| `source_commit` | String | Source commit from the verified release statement |

## GitHub API limits

GitHub normally permits 60 unauthenticated API requests each hour for one IP address.

Version discovery uses GitHub as a fallback. Standalone and Cargo updates also need GitHub release metadata for verification, even when npm discovery succeeds.

Set `GITHUB_TOKEN` or `GH_TOKEN` to use the authenticated limit of 5,000 requests each hour. Public repository metadata access is sufficient.

If a release request reaches its limit, LPM CLI reports the reset time. Wait for that time, or supply a token.

## CI

Do not run `lpm self-update` during a CI job. An update changes the toolchain during the job and makes the build less reproducible.

Pin an exact npm package version or standalone release instead. Change that pin in a reviewed project update.

Use [`lpm health`](/docs/infra/doctor#lpm-health) for a registry connectivity test.
