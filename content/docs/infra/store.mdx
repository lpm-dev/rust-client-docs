title: lpm store
description: "Find, verify, or reset the shared package store."
---

Use `lpm store` to inspect shared package data, diagnose corruption, or reset the store before a fresh install.

```bash
lpm store <COMMAND>
lpm store path [--json]
lpm store verify [--deep] [--fix] [--json]
lpm store clean [--json]
```

The `--deep` and `--fix` flags must follow `verify`. LPM CLI rejects `--deep` and `--fix` with `path` or `clean`.

## Quickstart

Run a fast verification of every store version:

```bash
lpm store verify
```

## Choose an action

| Action | What it does | Use case |
| --- | --- | --- |
| `path` | Prints the root of the shared store | You need the store path for inspection or a script |
| `verify` | Verifies v1, v2, and v3 store data | An install reports a store error, or you want an integrity check |
| `clean` | Immediately removes all v1, v2, and v3 store data | You need a complete reset and accept new downloads and builds |

## Store configuration

The default store path is `~/.lpm/store/`. `LPM_HOME` changes the parent directory for LPM CLI data:

```bash
LPM_HOME=/srv/lpm lpm store path
LPM_HOME=/srv/lpm lpm store verify --deep
```

`lpm.json` has no store configuration. All projects that use the same LPM CLI home share its package data, security caches, and native-build artifacts.

`lpm store path` prints the path without creating the store or acquiring its lock.

### Store versions

| Version | Status | Stored data |
| --- | --- | --- |
| v1 | Legacy | Complete package directories, identified by name and version |
| v2 | Default | Shared package objects and separate dependency layouts |
| v3 | Experimental | Shared file blobs, package-tree records, and dependency layouts |

The three versions can exist together. Verification and cleaning always cover all three versions, regardless of `LPM_STORE_VERSION`.

To select a layout for an install, set `LPM_STORE_VERSION` for that command:

```bash
LPM_STORE_VERSION=v3 lpm install
```

The values `v1`, `v2`, and `v3` select a version. The values `1`, `2`, and `3` are aliases.

An unset or empty value selects v2. An unknown value produces a warning and selects v2. LPM CLI never selects v3 automatically.

See [Content-addressable store](/docs/packages/content-addressable-store) for the storage model.

## Recipes

### Print the store path

```bash
lpm store path
```

If a diagnostic tool or script needs the active store root, use this command.

### Run a fast verification

```bash
lpm store verify
```

Fast verification requires a nonempty, regular `package.json` file. It examines package directories, link metadata, object references, and v3 store metadata.

It rejects redirected store roots and package directories, including symbolic links and Windows junctions. It also rejects linked manifests.

Normal dependency links inside a package layout remain supported. Fast verification does not parse manifests or rehash package bytes.

### Run a deep verification

Run this command from a project root:

```bash
lpm store verify --deep
```

Deep verification requires each `package.json` to contain a JSON object. If `name` or `version` is present, it must be a matching string.

Legacy manifests can omit those fields. Deep verification does not require them to exist.

Deep verification reads the applicable project lockfile, including a workspace member's view. It compares integrity through installed links and exact dependency relationships. It also rehashes v3 file blobs.

An unrelated store entry can share a package name and version but contain a different source. Verification does not compare that entry with another project's integrity.

Lockfile comparison requires installed project links that resolve to store entries. Legacy installs usually copy package files, so their comparison can remain partial. Missing integrity markers also leave records unexamined. Unreadable markers report an error.

If no applicable `lpm.lock` exists, LPM CLI skips the lockfile comparison. If an owning file is invalid or unreadable, verification fails.

### Refresh security caches

```bash
lpm store verify --fix
```

`--fix` implies deep verification. It refreshes missing or stale `.lpm-security.json` files with atomic replacement.

If a cache file is a symbolic link or hard link, replacement preserves the linked target. Redirected package directories fail verification before cache repair.

`--fix` does not restore missing packages or repair manifests and integrity errors. LPM CLI reports these errors for separate recovery.

### Use verification in CI

```bash
lpm store verify --deep --json > store-report.json
```

If verification finds corruption, it writes the JSON report and exits with status `1`.

Errors that prevent enumeration, such as a redirected store root, return a command error before the detailed report.

### Inspect v3 orphan counts

```bash
lpm store verify --json
```

Read the `cas.orphaned_*` fields for unreachable v3 data. Verification reports this data but does not remove it.

### Preview orphan removal

```bash
lpm cache prune          # preview removals
lpm cache prune --apply  # apply the removal plan
```

[`lpm cache prune`](/docs/packages/cache#prune-unused-packages) uses project references to retain required store entries. The preview does not remove data.

## Verification levels

For v1 and v2, deep verification compares saved integrity markers with the applicable lockfile. It does not recalculate integrity from extracted package bytes.

For v3, deep verification also rehashes stored file blobs. Oversized or unreadable source-integrity markers fail verification.


| Command | Package and link structure | `package.json` contents | `lpm.lock` integrity | v3 blob hashes | Security cache |
| --- | --- | --- | --- | --- | --- |
| `lpm store verify` | Verifies | Does not parse | Does not compare | Does not rehash | Does not analyze |
| `lpm store verify --deep` | Verifies | Parses and compares | Compares with the current lockfile | Rehashes | Reports missing or stale caches |
| `lpm store verify --fix` | Verifies | Parses and compares | Compares with the current lockfile | Rehashes | Reports and refreshes missing or stale caches |

## JSON output

Use the global `--json` flag with each action. Each action returns a different JSON object.

### `path` output

```bash
lpm store path --json
```

```json
{
  "success": true,
  "path": "/Users/you/.lpm/store"
}
```

| Field | Type | Meaning |
| --- | --- | --- |
| `success` | Boolean | `true` after LPM CLI resolves the store path |
| `path` | String | Absolute path to the store root |


#### Verification fields

| Field | Type | Meaning |
| --- | --- | --- |
| `success` | Boolean | If `issues` contains a corruption or write error, this value is `false` |
| `check_kind` | String | Compatibility alias for `legacy_check_kind` |
| `legacy_check_kind` | String | `presence` for fast verification or `lockfile_marker_consistency` for deep verification |
| `bytes_integrity_recomputed` | Boolean | `true` after deep verification rehashes at least one v3 blob |
| `entries_verified` | Integer | Number of store entries that completed verification without corruption |
| `verified` | Integer | Compatibility alias for `entries_verified` |
| `unique_coords` | Integer | Number of unique package name and version pairs |
| `duplicated_entries` | Integer | Entries repeated across store versions or dependency graphs |
| `corrupted` | Integer | Number of corruption or write errors in `issues` |
| `issues` | String array | Error messages for failed verification work |
| `lockfile_comparison` | Object | Deep verification only: lockfile comparison status and coverage |
| `securityMismatches` | Integer | Missing or stale security caches found by deep verification |
| `securityReanalyzed` | Integer | Security caches that `--fix` refreshed successfully |
| `cas` | Object | v3 file-store verification results |

`securityMismatches` and `securityReanalyzed` appear only during deep verification. A security mismatch alone does not set `success` to `false`.

#### Lockfile comparison

Deep JSON includes `lockfile_comparison`:

| Field | Meaning |
| --- | --- |
| `status` | `complete`, `partial`, `not_found`, or `unreadable`. |
| `packages` | Locked package records that contain integrity. |
| `compared_packages` | Records whose stored integrity was compared with the lockfile. |
| `uncompared_packages` | Records without a completed integrity comparison. |

`complete` describes coverage, not a successful result. Integrity mismatches still set `success: false` and exit with status `1`.

`partial` does not mean that the unexamined packages are corrupt. For example, a lockfile-only export can lack the installed links needed for comparison.

#### v3 `cas` fields

| Field | Type | Meaning |
| --- | --- | --- |
| `check_kind` | String | `metadata` for fast verification or `content_hash` for deep verification |
| `sources` | Integer | v3 source records examined |
| `trees` | Integer | v3 package-tree records examined |
| `blobs` | Integer | v3 file blobs examined |
| `blobs_rehashed` | Integer | v3 file blobs rehashed during deep verification |
| `materialized` | Integer | Reconstructed v3 package trees examined |
| `orphaned_sources` | Integer | Source records that no live store relationship reaches |
| `orphaned_trees` | Integer | Package-tree records that no live source reaches |
| `orphaned_blobs` | Integer | File blobs that no live package tree reaches |
| `orphaned_materialized` | Integer | Reconstructed package trees that no live source reaches |
| `blob_integrity_recomputed` | Boolean | `true` after deep verification rehashes at least one v3 blob |

## Reset the complete store

> **CAUTION:** If you need a complete reset, use `lpm store clean`. The command removes all store versions without a confirmation prompt.

```bash
lpm store clean
lpm install
```

The clean action removes package data, link entries, security caches, and native-build artifacts. It retains the outer store directory and control files.

If a version root is a symbolic link or junction, cleaning removes the link and preserves its target. Dangling version-root links are also removed.

A redirected outer store root is rejected before LPM CLI creates a lock file or removes data.

The next install downloads or rebuilds the required packages. For normal cleanup, use the reference-aware [`lpm cache prune`](/docs/packages/cache#prune-unused-packages) command.

If verification reports only security-cache differences, use `lpm store verify --fix`. These differences alone do not cause a failed exit status.

If package data is corrupt, inspect the reported paths. `--fix` cannot restore those files.

For corruption in unused data, preview [`lpm cache prune`](/docs/packages/cache#prune-unused-packages). For a complete reset, use the clean-and-install recipe above.

## Concurrent operations

Verification and installs can overlap. Both hold a shared store lock, so a complete store clean waits for them. Verification is not a snapshot of concurrent package changes.

The clean action waits for installs and other store readers to finish. New store readers wait while a clean action is queued.

After one second, a waiting command prints `Waiting for another lpm store operation to finish...`. LPM CLI releases its locks automatically.

## Flags

| Flag | Applies to | Effect |
| --- | --- | --- |
| `--deep` | `verify` | Parses manifests, compares lockfile integrity, and rehashes v3 blobs |
| `--fix` | `verify` | Refreshes missing or stale security caches and implies `--deep` |
| `--json` | All actions | Prints the action result as JSON |

See the [global flags](/docs/commands#global-flags).
