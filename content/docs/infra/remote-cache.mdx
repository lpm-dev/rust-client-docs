---
title: Remote task cache
description: "Reuse task outputs across developer machines and CI jobs with the LPM.dev Registry."
---

Remote caching shares completed task results across machines. Use it for repeatable builds whose inputs and output files are known.

[`lpm run`](/docs/dev/run) restores matching outputs and replays the task's logs. The LPM.dev Registry stores the shared artifacts.

## How it works

For each task with caching enabled, LPM CLI follows this order:

1. Check the local task cache at `~/.lpm/cache/tasks/`.
2. On a local miss, check the remote cache for the same task key.
3. If both caches miss, run the task command.

A successful task writes the local cache first. With remote uploads enabled, LPM CLI then uploads the declared output files, stdout, stderr, and task metadata.

A remote hit also populates the local cache. Failed tasks do not publish cache entries.

Remote caching reuses task results. Package downloads and offline dependency installs use the separate [package store](/docs/infra/store).

## Quickstart

This example assumes a `build` script in `package.json` that writes to `dist/`. Hosted storage requires a Pro personal account or an eligible Organization account.

### 1. Enable caching in `lpm.json`

```json title="lpm.json"
{
  "$schema": "https://cli.lpm.dev/schemas/lpm.json",
  "remoteCache": {
    "enabled": true
  },
  "tasks": {
    "build": {
      "cache": true,
      "cacheEnv": ["NODE_ENV"],
      "outputs": ["dist/**"]
    }
  }
}
```

Merge these fields into your existing configuration. Adjust `outputs` to match the files that the build produces.

`cache: true` requires a non-empty `outputs` list. Without both fields, the task runs without caching.

The example hashes `NODE_ENV` from the inherited environment. Add every other inherited variable that can affect your build.

### 2. Authenticate

Create a personal token with the `cache:write` scope in [Registry token settings](https://lpm.dev/dashboard/settings/tokens).

Set the token in your shell environment:

```bash
export LPM_REMOTE_CACHE_TOKEN="<cache-write-token>"
export NODE_ENV=production
```

The token permits cache reads and writes. Supply it through the shell or CI environment, outside committed project configuration.

For the configured Registry origin, LPM CLI can also use `LPM_TOKEN`, when it's a token that permits cache access, or your [`lpm login`](/docs/infra/login) credentials. Login credentials read and write your personal cache. An organization's cache needs one of its tokens.

### 3. Run the task

```bash
lpm cache status
lpm run build
```

After a successful upload, another machine with the same cache key and namespace can restore the result.

A second run on the same machine normally uses the local cache. [`lpm cache status`](/docs/packages/cache#status) reports service availability, usage, and quota.

## Share with a team and CI

### Organization access

Create an organization token in the organization's **Settings → Tokens** page. Use `cache:write` for producers or `cache:read` for consumers.

Add the organization slug to the existing `remoteCache` configuration:

```json title="lpm.json"
{
  "remoteCache": {
    "enabled": true,
    "team": "acme"
  }
}
```

Set `LPM_REMOTE_CACHE_TOKEN` to a token scoped to `acme`. A personal token cannot access the organization cache merely by selecting its slug.

If `team` is omitted, the token selects the namespace: personal tokens use personal storage, and organization tokens use organization storage.

`LPM_REMOTE_CACHE_TEAM` overrides the configured team for one process. It selects a namespace without granting additional permissions.

| Token scope | Download artifacts | Upload artifacts |
| --- | --- | --- |
| `cache:read` | Yes | No |
| `cache:write` | Yes | Yes |
| `admin` | Yes | Yes |
| `read` or `publish` | No | No |

### CI producer

Store the cache token as a CI secret. After checkout, CLI installation, and dependency installation, run the build:

```yaml title="GitHub Actions build step"
- name: Build with remote cache
  run: lpm run build
  env:
    NODE_ENV: production
    LPM_REMOTE_CACHE_TOKEN: ${{ secrets.LPM_REMOTE_CACHE_TOKEN }}
```

The committed `lpm.json` enables remote caching and selects the task. For complete runner setup, see the [CI/CD guide](/docs/guides/ci-cd-setup).

Cache scopes do not grant package-read permission. Private dependency installation can use a separate `LPM_TOKEN` on its own step.

### Read-only consumers

Use a `cache:read` token and disable uploads for jobs that only consume shared results:

```yaml title="GitHub Actions read-only build step"
- name: Build with read-only remote cache
  run: lpm run build
  env:
    NODE_ENV: production
    LPM_REMOTE_CACHE_TOKEN: ${{ secrets.LPM_REMOTE_CACHE_READ_TOKEN }}
    LPM_REMOTE_CACHE_READ_ONLY: "1"
```

A cache miss still runs the task and stores its result locally. The read-only setting skips remote uploads.

For a persistent setting, use `remoteCache.readOnly: true`. `LPM_REMOTE_CACHE_READ_ONLY=0` does not override that setting.

## Make cache hits predictable

The key includes source inputs, the command, arguments, project configuration, manifests, lockfiles, runtime identities, environment values, and task dependencies.

See [Task runner — Cache key](/docs/dev/task-runner#cache-key) for the complete contract.

### Declare the build contract

- Set `inputs` to include every source and configuration file that affects the result.
- Set `outputs` to include every generated file that another machine needs.
- Pin runtime and dependency versions across producers and consumers.
- Use the same task configuration on each machine.

The complete `lpm.json` affects the key. For CI-only read-only behavior, an environment override preserves the shared configuration file.

### Declare output files precisely

Output patterns select regular files relative to the project root. Multiple patterns combine their matches.

| Pattern | Files included |
| --- | --- |
| `dist/*` | Files directly inside `dist/`. |
| `dist/**` | Files inside `dist/` at any depth. |
| `dist/**/*.js` | JavaScript files inside `dist/` at any depth. |
| `report.json` | One file at the project root. |

An output pattern that starts with `!` matches a literal name. It does not exclude files from another pattern.

```json title="lpm.json task fragment"
{
  "tasks": {
    "build": {
      "cache": true,
      "cacheEnv": ["NODE_ENV"],
      "outputs": ["dist/**", "reports/build.json"]
    }
  }
}
```

Local and remote restores accept only files that match the current output patterns. A file outside those patterns rejects the entire restore.

An accepted restore removes stale files that match the same patterns but are absent from the cached result. Other project files remain unchanged.

Declare generated files only. Do not include source files or configuration that the task must preserve.

### Choose inherited variables with `cacheEnv`

Without `cacheEnv`, all inherited variables visible to the task affect its key. Machine paths and CI run identifiers can therefore prevent reuse.

`cacheEnv` selects exact, case-sensitive inherited variable names. It does not support wildcards.

```json title="lpm.json task fragment"
{
  "tasks": {
    "build": {
      "cache": true,
      "cacheEnv": ["NODE_ENV", "BUILD_TARGET"],
      "outputs": ["dist/**"]
    }
  }
}
```

An empty list excludes all inherited variables from the key. Use it only for a task whose output does not depend on those variables.

Project-loaded variables, including dotenv and local secrets, always affect the key. `cacheEnv` does not change the task's environment or its upload eligibility.

### Bypass caching for one run

Disable only remote caching:

```bash
LPM_REMOTE_CACHE=0 lpm run build
```

Bypass both local and remote task caching:

```bash
lpm run build --no-cache
```

Watch mode runs tasks without the task cache. See [`lpm run --watch`](/docs/dev/run#watch-finite-tasks).

## Protect cached artifacts

Cache artifacts include build files and captured logs. Anyone with read access to the namespace can download them.

### Signed artifacts

Set `remoteCache.signature` to `true` to require signatures. Give every producer and consumer the same private signing key:

```bash
export LPM_REMOTE_CACHE_SIGNATURE_KEY="<shared-signing-key>"
```

Store a randomly generated key in your secret manager and CI secrets. Add the variable to the CI steps that use the cache.

Every download requires a matching content hash. With a signing key configured, it also requires a valid HMAC signature before restore.

Signatures authenticate artifacts. They do not encrypt their contents.

LPM CLI checks the complete archive before it changes project outputs. It rejects undeclared files, directory entries, links, and unsafe paths.

Empty directories are not cached. LPM CLI creates parent directories as needed for declared files.

### Secrets and upload policy

By default, secret-looking variables visible to a task block remote uploads. Examples include `DATABASE_URL`, names containing `TOKEN` or `SECRET`, and names ending in `_KEY`.

This rule also applies to [local project secrets](/docs/dev/lpm-vault). The task and local caching still work.

The [`remoteCache.env` fields](/docs/reference/lpm-json#remotecache) control upload eligibility:

| Field | Effect |
| --- | --- |
| `exclude` | Block uploads when a visible variable name matches a pattern. |
| `include` | Allow matching names through the default secret-name check. |
| `allowSecrets` | Allow secret-looking names unless an `exclude` pattern blocks them. |

Patterns are case-insensitive and support `*`. Exclusions take precedence over inclusions.

These fields do not redact logs, remove environment values, or sanitize output files. Allow a name only after you determine that its outputs are safe to share.

Cache credentials belong in the parent shell or CI environment. Project dotenv and local secrets configure the task, not the cache client's credentials.

### Custom cache endpoints

`remoteCache.url` or `LPM_REMOTE_CACHE_URL` can select another compatible cache service. The default is the configured Registry URL plus `/v8`.

An endpoint outside the configured Registry origin requires both `LPM_REMOTE_CACHE_TOKEN` and `LPM_REMOTE_CACHE_SIGNATURE_KEY`. The Registry login token is never sent to that endpoint.

Remote endpoints require HTTPS. HTTP is also accepted for `localhost`, `127.0.0.1`, and `[::1]`.

For example, select a compatible local service for one run:

```bash
LPM_REMOTE_CACHE_URL="http://[::1]:3000/v8" lpm run build
```

The credential and signing-key requirements still apply to a different Registry origin.

## Usage and retention

The LPM.dev Registry applies these included storage limits:

| Account | Included remote cache |
| --- | --- |
| Free personal | None |
| Pro personal | 25 GiB |
| Organization | 25 GiB per seat |
| Enterprise | No fixed quota in the Enterprise plan |

The LPM.dev Registry accepts archives up to 100 MiB (104,857,600 bytes). LPM CLI skips uploading a larger archive to it and builds the task as usual. With a [custom cache endpoint](#custom-cache-endpoints), LPM CLI uploads and restores archives up to 500 MiB.

Restore also applies these limits to the archive contents:

| Limit | Maximum |
| --- | --- |
| One extracted file | 256 MiB |
| Total extracted content | 1 GiB |
| Archive entries | 100,000 |

A compressed archive can fit the upload limit but exceed an extraction limit. A rejected download becomes a cache miss.

Default retention is 14 days, and a download refreshes the retention period.

To fit new uploads within the storage limit, the Registry can evict the least recently accessed artifacts. Cache storage is temporary.

### Request limits

The LPM.dev Registry limits the remote cache requests of each Pro account, and of each organization seat, Enterprise included:

| Limit | Per minute | Per day |
| --- | --- | --- |
| Requests of any kind | 3,000 | 100,000 |
| Uploads | 300 | 4,000 |
| Uploaded data | - | 12 GiB |
| Cache hits | 2,000 | 50,000 |
| Downloaded data | - | 40 GiB |
| Of which downloaded through the Registry | - | 5 GiB |

- Every request whose token may use the account's cache for it counts against its request limits, including lookups that miss and status checks. A query for several artifacts at once counts one request for each different artifact; one with more than the window has left is refused and counts as one request.
- LPM CLI and Turborepo download a cache hit from the cache's download host, `cache-dl.lpm.dev`, through a link the Registry answers with that works for a minute, so a CI firewall must allow that host too. The host refuses a request carrying an `Origin`, `Forwarded`, `X-Forwarded-Host` or similar header with HTTP 403, so a TLS-inspecting proxy that adds one turns every cache hit into a miss, and the task runs again. Turborepo downloads a signed artifact through the Registry instead, as do other clients and older LPM CLI releases; those downloads also count against the 5 GiB a day of downloads through the Registry. LPM CLI treats an artifact uploaded without a content hash, as Turborepo uploads one, as a miss, and replaces it with its own.
- Uploads also count against the upload limits, and cache hits against the cache-hit limits. A cache hit is a download, or an existence check, that finds the artifact. An upload the Registry refuses before receiving it doesn't count as an upload, and neither does one of content the cache already holds, recognized by the checksum LPM CLI sends; the check that storage still holds it counts as a cache hit, and content storage has lost is stored again. Once the account's cache hits are spent, such an upload is stored, and counted, as any other.
- An organization's daily limits grow with every seat. Its limits a minute grow with up to ten seats, and its uploads a minute with up to five: 1,500 uploads a minute.
- An account can have 4 uploads in flight for each seat, at least 8 and at most 16, across the Registry, and 8 uploads and downloads together for each seat, at least 32 and at most 64, on each Registry server. A Registry server that is half full shares its places equally among the accounts using it, and keeps a few places for accounts using few. With every place taken, it answers as busy until a place frees.
- An upload, or a download through the Registry, that takes longer than 10 seconds plus a second for every 128 KiB, or longer than 2 minutes, is cut off. LPM CLI gives each remote cache request 30 seconds anyway. After an interrupted download the task runs as on a miss, and the hit and its bytes still count.
- An upload that stops partway, such as when its connection drops, holds its artifact for at most 5 minutes.
- An account whose plan has no remote cache gets 30 requests a minute and 1,000 a day, counted apart from its requests before its plan changed. An organization whose billing lapsed gets HTTP 402 to every request except status checks, which report `paused`; while the Registry checks again whether that still holds, other requests get a brief HTTP 429 with `Retry-After: 1`.
- A request the Registry refuses is answered with why, such as HTTP 403 for an upload with a read-only token or a request for another account's cache, or HTTP 400 for a request that isn't valid. It counts against limits of its own instead of the request limits above, whatever the seats: 30 a minute and 1,000 a day for its token, and 120 a minute and 5,000 a day for the token's account. Once one of these limits is spent, the Registry still answers each request as before. A token reaches only its own account's cache: `slug` or `teamId` naming any other gets HTTP 403, whether or not that account exists, and a `slug` and `teamId` of which only one names the token's own account get HTTP 400.
- With a token that can only read the cache, run Turborepo with `--remote-cache-read-only`. Without it, Turborepo turns its remote cache off for the run after its first refused upload.
- LPM CLI stops uploading for the run after its first refused upload, and stops using the remote cache for the run after a refused lookup, or once the organization's billing lapses. An upload the cache has no room for is skipped on its own, as the cache makes room and a later one may fit.
- The Registry checks a token at most once a minute on each server, so a revoked token can keep working for up to a minute. When LPM CLI refreshes an `lpm login` session, the session's previous access token stops working within five minutes, and any older one at once, or within that minute on a server that checked it.
- A token that isn't valid gets the same HTTP 401 for a minute. After 60 tokens from one address in a minute that aren't valid, or whose requests are refused, over their account's request limits, answered that the organization's billing lapsed, sent to a cache that can't serve them (status checks included), or new tokens told to wait while the account's limits are checked, from one address or one IPv6 /64, or 240 from one IPv6 /48, a Registry server answers that address with HTTP 429 for the rest of the minute. Each server counts on its own. It still checks one token from there every 2 seconds, and lets through a token whose requests it served in the last 23 hours, until the token stops being valid, or one of its requests is refused, over the account's request limits, answered that the organization's billing lapsed, or sent to a cache that can't serve it, a status check that finds the cache can't serve reads included. A status check serves a token only when its account's cache serves reads: `enabled` or `over_limit`. New tokens still being checked count toward those 60 too, until their requests are answered, so while that many are in progress from one address, a further new token gets HTTP 429 with `Retry-After: 1` ("Too many new tokens from this address are being checked"); a token served lately isn't held up.

Each window starts with the first request it counts, not at a set time of day.

A request past a limit gets HTTP 429 with a `Retry-After` header that gives the seconds until the limit resets. LPM CLI then skips that kind of request until then, and builds tasks as it would without a remote cache. A lookup limit pauses uploads too, since a task that skipped its lookup would likely upload an artifact the cache already holds. The CLI warns once a run for each kind of limit.

A wait of 5 seconds or less usually means the Registry is busy for a moment, or a minute's window is about to reset. LPM CLI sends such a lookup or upload once more after the wait, plus up to half the wait again so refused requests don't all return together, unless that kind was paused meanwhile. If it skips some anyway, it notes it once a run for each kind, as `remote cache is busy; skipping some uploads for a moment` (or lookups), and keeps the limit warning for a longer limit.

Turborepo receives a per-minute limit as HTTP 429, and a daily limit as HTTP 403 with the code `remote_caching_over_limit`.

### Inspect usage

```bash
lpm cache status
lpm cache status --json
```

The dashboard's **Settings → Billing** page shows remote-cache usage, retention, and overage controls for the selected account.

Overage is off by default. Enabling it permits uploads above the included quota, subject to any account overage cap.

An organization owner or administrator controls its overage setting.

| Remote status | Meaning |
| --- | --- |
| `enabled` | Remote caching is available within the account's limits. |
| `disabled` | The plan or account configuration disables remote caching. |
| `paused` | Remote access is paused, including after organization billing lapses. |
| `over_limit` | Usage exceeds the allowed storage. Existing artifacts remain readable, and uploads first attempt eviction. |

Organization access continues during the billing grace period. After billing lapses, reads and uploads stop until the subscription is restored.

[`lpm cache clean tasks`](/docs/packages/cache) clears the local task cache. It does not delete hosted artifacts or reduce remote usage.

## Troubleshooting

### Every machine rebuilds

Make sure that producers and consumers use the same namespace, inputs, runtime versions, and task configuration. Inspect `cacheEnv` for missing or machine-specific selections.

Project-loaded environment values also affect the key. Different dotenv or local secret values can produce different keys.

### Uploads are skipped

Make sure that the task declares `cache: true` and `outputs`. Inspect warnings for a read-only token, missing signing key, secret-looking variable, or artifact size limit.

If read-only mode is enabled, uploads are skipped by design. A local hit also avoids task execution and does not upload an existing local result.

### A request limit is reached

LPM CLI warns `Remote cache limit reached` with the limit it reached and how long it skips remote requests. Tasks still run, and the CLI uses the remote cache again once the limit resets. See [Request limits](#request-limits).

Concurrent runs, such as parallel CI jobs, share the account's limits. To spend fewer requests:

- Give jobs that only consume results [read-only access](#read-only-consumers), so they don't upload.
- Cache only tasks that take longer to run than to download. Each cached task costs a lookup on every run, and an upload on every miss.

The Registry also answers with HTTP 429 and `Retry-After: 1` when the account has as many uploads or downloads in flight as it may, while another upload holds its cache, while it checks again whether the account's limits still hold, or while as many new tokens from one address are being checked as it would gate, and with `Retry-After: 2` when the Registry server is busy. LPM CLI sends a refused lookup or upload once more after the wait, plus up to half of it again, and notes `remote cache is busy; skipping some uploads for a moment` (or lookups) if it skips some anyway. An upload of an artifact another upload is still storing gets HTTP 409, and LPM CLI leaves it to that upload.

### The server rejects access

Make sure that the token has `cache:read`, `cache:write`, or `admin` permission. Uploads require `cache:write` or `admin`. Credentials from `lpm login` read and write your personal cache only.

For an organization, use a token scoped to the selected organization. Inspect the account's plan and billing state with [`lpm cache status`](/docs/packages/cache#status).

### Signatures fail

Make sure that producers and consumers use the same signing key. Unsigned artifacts cannot satisfy a signed read.

A rejected artifact becomes a miss, and LPM CLI runs the task locally. A successful run can upload a replacement with the configured key.

### An archive contains undeclared output files

Check that the producer and consumer use the same task configuration. Confirm that `outputs` includes every generated file needed by the task.

LPM CLI rejects the archive before it replaces or removes project outputs. The task then runs locally and can publish a valid replacement.

### The cache service is unavailable

Remote timeouts, missing artifacts, and rejected downloads do not stop local task execution. Upload failures do not turn a successful task into a failure.

The JSON output from [`lpm cache status`](/docs/packages/cache#status) includes `remote.error`. Even when the command exits successfully, inspect this field.
