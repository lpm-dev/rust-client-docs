---
title: lpm run
description: "Run project tasks with dependencies, parallel output, workspace selection, and optional caching."
---

Run package scripts and configured tasks. Use task dependencies to put checks before builds, and workspace filters to select packages.

```bash
lpm run [OPTIONS] <SCRIPTS>... [-- <ARGS>...]
```

## Quickstart

```bash
lpm run build
lpm run lint test
lpm run lint test --parallel --stream
lpm run test -- --run
```

Without `lpm.json`, LPM CLI uses the scripts in `package.json`.
It adds project and workspace executables from `node_modules/.bin` to the command's `PATH`.

| Mode | Behavior |
| --- | --- |
| Default | Run the requested tasks and their prerequisites in order |
| `--parallel` | Run independent tasks concurrently |
| `--all`, `--filter`, `--filter-prod`, `--affected` | Select workspace members |
| `--watch` | Repeat one requested task and its prerequisites after file changes |

## Configure `lpm.json`

```json title="lpm.json"
{
  "tasks": {
    "check": {
      "command": "tsc --noEmit"
    },
    "build": {
      "command": "vite build",
      "dependsOn": ["check"],
      "env": "production",
      "cache": true,
      "inputs": ["src/**", "index.html", "vite.config.ts", "package.json"],
      "outputs": ["dist/**"]
    },
    "verify": {
      "dependsOn": ["check", "build"]
    }
  }
}
```

```bash
lpm run build
lpm run build --env staging --no-cache
lpm run verify
```

The build runs after `check` succeeds. The `verify` task groups prerequisites and needs no command of its own.

A task's `command` overrides the package script with the same name.
Without this field, LPM CLI uses the package script.
Projects can define commands entirely in `lpm.json`.

| Task field | Purpose | One-run override |
| --- | --- | --- |
| `command` | Shell command for the task | Append command arguments after `--` |
| `dependsOn` | Local prerequisites or upstream workspace tasks such as `^build` | No prerequisite bypass |
| `env` | Named environment or environment-file mapping | `--env <ENV>` |
| `cache` | Enable caching with declared outputs | `--no-cache` |
| `inputs` | Files that affect the cache key and watch scope | No input override |
| `outputs` | Files to save and restore with cached results | `--no-cache` disables cache use |
| `cacheEnv` | Inherited variable names to include in the cache key | No variable-selection override |

See the [configuration reference](/docs/reference/lpm-json) for the complete schema.

## Command arguments and hooks

```bash
lpm run build -- --mode staging
```

Arguments after `--` go to each executed main task, including prerequisites. They do not go to package pre/post hooks.
Shell metacharacters in forwarded arguments remain argument data.
On Windows, forwarded arguments cannot contain line breaks.

Package scripts run `pre<name>`, the main script, then `post<name>`.
A failed phase stops the later phases.
An explicit task command does not use package pre/post hooks.

Each package phase receives [npm script context](/docs/packages/npm-compatibility#script-execution), including its package identity, declared command, and original invocation directory.

## Task order and failures

Without `--parallel`, independent tasks keep the order from the command line. Prerequisites always run before their dependents.

```bash
lpm run lint test build --parallel
lpm run lint test build --parallel --no-bail --stream
```

By default, a failure prevents the next batch from starting. Already running tasks finish.
With `--no-bail`, independent tasks continue. Tasks whose prerequisites failed remain skipped.

`--stream` shows live output with task prefixes, including sequential runs and levels with one task.
Cached logs use the same prefixes. The global color setting also applies to streamed output.
Parallel output is otherwise buffered per task.
Captured logs have a 10 MiB limit per stream across the task's phases.
Live output continues after the capture limit.

A single task without prerequisites preserves its child exit code.
A run with several tasks returns the number of failed tasks.
Workspace runs return a nonzero status if a scheduled member fails.

## Workspaces

```bash
lpm run build --all
lpm run build --filter web --filter api
lpm run build --filter './packages/*' --workspace-concurrency 2
lpm run test --affected --base origin/main
lpm run build --filter-prod '...shared'
```

Workspace modes require a workspace. The current directory identifies the project for ordinary single-package runs.

Repeated filters select the union of their matches. Filters and `--affected` also combine by union.
`--all` cannot be combined with either filter flag or `--affected`.

Filters match package names, paths, dependency closures, or Git changes.
For example, `--filter core` does not match `@babel/core`. Use `--filter '*/core'` for scoped names.
See [workspace filters](/docs/packages/workspaces) for the full grammar.

### Upstream tasks

```json title="packages/web/lpm.json"
{
  "tasks": {
    "build": {
      "dependsOn": ["^build"]
    }
  }
}
```

The selected package's build waits for `build` in its upstream workspace dependencies.
This expansion covers the full dependency chain and can include packages outside the original filter.
LPM CLI checks the expanded graph before it starts task processes.

With `--no-bail`, other selected members continue after a failure.
A failed explicit `^task` prerequisite still prevents its dependent task from running.

### Concurrency and changed files

`--workspace-concurrency <N>` limits concurrent members within each dependency level.
The default comes from `lpm.toml` under `[workspace].concurrency`, then `~/.lpm/config.toml` under `workspace-concurrency`, then available processors.
`--parallel` separately controls independent tasks inside each member.

```bash
lpm run test --affected --changed-files-ignore-pattern '**/README.md'
lpm run test --affected --test-pattern '**/*.test.js'
```

Ignored paths do not affect Git-based selection.
Test-only changes still select their package, but do not select its dependents through affected-package expansion.
Project defaults also come from the matching keys under `lpm.toml`'s `[workspace]` table.

## Environments and runtimes

```bash
lpm run start --env staging
lpm run start --no-env-check
```

Environment selection uses `--env`, then `tasks.<name>.env`, then `env.<name>`, then the default environment.
Named environments can define an inheritance chain or a custom file path.
Standard loading reads `.env`, `.env.local`, `.env.<MODE>`, then `.env.<MODE>.local`.
Without a mode, it reads the first two files.

Later files override earlier files. Safe inherited values take precedence over file values.
Project secrets from [lpm env](/docs/dev/env) override file values.
Configured files and symlinks must remain inside the project.

LPM CLI strips inherited credentials and protected runtime variables before it starts project commands.
Explicit project secrets remain available. Files, secrets, and schema defaults cannot inject protected runtime hooks such as `NODE_OPTIONS`.

The environment schema checks effective values and supplies configured defaults.
`--no-env-check` skips both schema checks and defaults.

Runtime selection uses the project's [runtime configuration](/docs/dev/use), including supported version files.
Missing managed runtimes can download automatically. By default, the selected Node version must satisfy applicable `engines.node` requirements.
The command does not install project dependencies. Use [lpm install](/docs/packages/install) first.

## Cache task results

A task needs `cache: true` and nonempty `outputs` to use the cache.
Only successful results enter the cache.

```bash
lpm run build
lpm run build --no-cache
```

The cache key includes the command, arguments, input files, environment, runtime identity, and prerequisite identities.
An empty `inputs` list uses the default source and configuration patterns.
Declare additional inputs if the build reads other files.

By default, inherited variables also affect the key.
`cacheEnv` selects those inherited names. An empty array excludes inherited values.
Variables loaded from project files, local secrets, and schema defaults remain cache inputs.
Include every inherited value that can change the output.

A cache hit restores outputs and replays captured logs without running the task.
The local cache is under `~/.lpm/cache/tasks/`.
With `remoteCache.enabled`, LPM CLI also uses the hosted cache. Remote cache failures become cache misses.

Use [lpm cache](/docs/packages/cache) to inspect or clear cached results.
See [remote task cache](/docs/infra/remote-cache) for account setup and CI configuration.

## Watch finite tasks

```bash
lpm run build --watch
lpm run verify --watch --parallel --stream
```

Watch mode runs one requested task and its prerequisites, then waits for changes.
Each run finishes before another starts. Changes during a run schedule a later run.
For development servers, use [lpm dev](/docs/dev/dev) or the framework's own watch mode.

Watch mode uses the inputs of the scheduled tasks and ignores their declared outputs.
Use a directory glob such as `dist/**` for a generated tree, including its directory changes.
It also ignores `.git`, `node_modules`, `.lpm`, and common editor temporary files.
Task configuration changes update the graph and watch scope. Restart the session after runtime-pin changes.

Watch runs bypass the task cache.
`--watch` cannot be combined with multiple requested task names, workspace selection, or `--json`.

## Non-interactive and JSON use

```bash
lpm run build --filter web --fail-if-no-match --json
lpm run lint test --no-bail --json
```

Task commands control their own prompts. Use their non-interactive flags after `--` where necessary.
`--fail-if-no-match` makes an empty workspace selection fail, which catches misspelled filters in CI.

With `--json`, child output and cache logs go to stderr. Stdout contains one result object.

| Mode | Result fields |
| --- | --- |
| Single package | `success`, `total`, `passed`, `failed`, `skipped`, `cached`, `duration_ms`, `tasks` |
| Workspace | `success`, `packages`, `succeeded`, `duration_ms` |

Each task includes `name`, `success`, `cached`, `skipped`, and `duration_ms`.
Failures can also include `exit_code` and `phase`. Logs and skip reasons are not embedded in task entries.

The workspace package count includes members added through `^task` expansion.
It excludes selected members without the requested task.
An empty selection without `--fail-if-no-match` returns a successful result with zero packages.

## Shortcuts and hidden scripts

```bash
lpm typecheck
lpm run .build
```

An unknown top-level command can select a script or task with the same name.
Built-in commands take precedence. For example, [lpm test](/docs/dev/test) uses runner detection, while `lpm run test` selects the task.

Use `lpm run` for task-runner flags. Arguments after a shorthand name go to the task itself.
If no script or task matches, shorthand tries a [project-local executable](/docs/dev/exec).
Path-like commands use the [source-file runner](/docs/dev/exec).

A package script whose name starts with `.` is a hidden helper.
Direct calls such as `lpm run .build` fail. Visible scripts and task dependencies can call it.
Hidden scripts do not appear in script listings or missing-script suggestions.

## Troubleshooting

| Problem | Recovery |
| --- | --- |
| Missing executable | Run [lpm install](/docs/packages/install) and check the script's command |
| Task is skipped | Correct the failed prerequisite, then run the task again |
| Unexpected cached output | Check `inputs`, `outputs`, and `cacheEnv`, then run with `--no-cache` |
| Workspace task is missing | Define the requested task in every package that an explicit dependency requires |
| No workspace matches | Check the [filter grammar](/docs/packages/workspaces) and package names |
| Watch never completes its first run | Use a finite command, or use [lpm dev](/docs/dev/dev) for the server |

## Flags

| Flag | Effect |
| --- | --- |
| `--env <ENV>` | Override the selected environment |
| `--parallel`, `-p` | Run independent tasks concurrently |
| `--no-bail` | Continue independent tasks or workspace members after failure |
| `--stream` | Show live output with task prefixes |
| `--all` | Select all workspace members |
| `--filter <FILTER>` | Select workspace members with a repeatable filter |
| `--filter-prod <FILTER_PROD>` | Apply filters with production-only dependency closures |
| `--fail-if-no-match` | Fail if workspace selection is empty |
| `--workspace-concurrency <N>` | Limit concurrent workspace members |
| `--affected` | Select packages affected by Git changes |
| `--base <BASE>` | Git base for affected selection. Default: `main` |
| `--changed-files-ignore-pattern <PATTERN>` | Exclude changed paths from Git-based selection. Repeatable |
| `--test-pattern <PATTERN>` | Treat matching changed paths as test-only. Repeatable |
| `--no-cache` | Bypass task caching |
| `--no-env-check` | Skip schema checks and defaults |
| `--watch` | Repeat a finite task graph after file changes |

The [global flags](/docs/commands#global-flags) include `--json`.
