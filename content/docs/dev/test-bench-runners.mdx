---
title: Test and bench runners
description: "Understand runner selection, project configuration, and results from test and benchmark commands."
---

[lpm test](/docs/dev/test) and [lpm bench](/docs/dev/bench) choose a runner from the package manifest.
Each selected workspace member can use a different runner.

```bash
lpm test
lpm bench
lpm test --filter web -- --coverage
```

## Runner selection

LPM CLI reads `dependencies` and `devDependencies` in `package.json`.
Declaration order does not change runner priority.

| Command | Priority |
| --- | --- |
| [lpm test](/docs/dev/test) | Vitest, Jest, Mocha, then `scripts.test` |
| [lpm bench](/docs/dev/bench) | Vitest, then `scripts.bench` |

A declared runner takes priority over the package script.
Detection does not install the runner.
If its executable is missing, run [lpm install](/docs/packages/install).
LPM CLI searches local executables within the current project or workspace.

For an explicit package script, use [lpm run](/docs/dev/run):

```bash
lpm run test
lpm run bench
```

Use package scripts for other runners, such as `node --test` or `bun test`.
A declared Vitest, Jest, or Mocha dependency can still take priority for the dedicated test command.

## Project configuration

The commands have no dedicated `test` or `bench` section in `lpm.json`.
They use project environment configuration and managed runtime pins.

```json title="lpm.json"
{
  "runtime": { "node": "22" },
  "env": { "test": ".env.test", "bench": ".env.bench" }
}
```

For package-script fallback, `tasks.<name>.env` takes priority over `env.<name>`.
If `tasks.<name>.command` exists, the package script remains the command.
Pre-hooks and post-hooks run in sequence with npm lifecycle variables.
A failed phase stops later phases.
Extra arguments apply to the main script.

Direct runners use the default project environment.
Both paths apply environment schemas and managed runtimes.
The dedicated commands do not use task caching or task dependencies.
See [lpm run](/docs/dev/run) for those workflows.

Workspace members inherit root runtime pins and can override each runtime locally.
Engine checks use the Node executable on the execution PATH.
See [managed runtimes](/docs/dev/node-version-pinning) for automatic downloads and fallback behavior.

## Arguments and watch mode

Put runner arguments after `--`:

```bash
lpm test -- --coverage
lpm test -- --all
lpm test --filter web -- --watch
lpm bench --filter web -- --watch
```

Vitest tests run once by default.
For an explicit watch request, LPM CLI removes the default `run` argument.
Use `--watch=false` to disable Vitest watch mode.
Vitest treats `--watch=off` and `--watch=0` as enabled.

Jest's `-w <N>` controls worker count.
Its `--watch` and `--watchAll` flags request watch mode.
Mocha receives its own watch arguments directly.
A package script controls its own runner behavior.

A workspace watch request can select exactly one member.
LPM CLI rejects watch requests that select multiple members.
For an empty selection, an explicit long watch flag reports that there is nothing to watch.

## Results and cleanup

Human mode streams child output to the terminal.
JSON mode closes stdin and emits one result after completion:

```bash
lpm --json test
lpm --json bench --all
```

The result contains member status, exit codes, and elapsed time.
Failed members include captured output or a launch error.
Successful members omit captured output.
Each captured stream has a 10 MiB limit.

Single-package runs preserve the runner or hook exit code.
If any selected member fails, workspace runs exit with `1`.
Their member results retain the individual exit codes.
Preparation failures use the global error object or a member error with `exit_code: null`.

On Unix, stop signals trigger child cleanup before LPM CLI exits.
A daemon that detaches and outlives its parent manages its own shutdown.
SIGINT produces status `130`, and SIGTERM produces `143`.
In JSON mode, bounded output remains available in the failure result.

See the command pages for complete workspace selectors, concurrency, and recovery examples.
