---
title: Local secrets
description: Store project secrets outside your repository and load them into applications with LPM CLI.
---

Local secrets keep project values in protected storage outside your repository. [lpm env](/docs/dev/env) manages them without an account or application SDK.

[lpm dev](/docs/dev/dev) and [lpm run](/docs/dev/run) load the values before they start your application.
The application reads normal environment variables, such as `process.env.API_TOKEN` in Node.js.

## Quickstart

From the directory that contains `package.json`, store a value and start an existing script:

```bash
lpm env set API_TOKEN=example-token
lpm env list
lpm run start
```

The first write adds a `vault` ID to `lpm.json`. `list` masks values by default.
These commands need no desktop app, plaintext export, or cloud connection.

## Project identity and configuration

The generated `vault` field associates the project with its local secrets:

```json title="lpm.json"
{
  "$schema": "https://cli.lpm.dev/schemas/lpm.json",
  "vault": "7f3a1e2c-5b9d-4a8f-b6c1-9b1d2e3f4a5b",
  "tasks": {
    "dev": { "env": "development" },
    "start": { "env": "staging" }
  },
  "envSchema": {
    "vars": {
      "API_TOKEN": { "required": true, "secret": true },
      "PORT": { "default": "3000", "format": "port" }
    }
  }
}
```

Keep the generated ID when you add configuration. Do not replace it with this example ID.
Commit `lpm.json` with the project. The ID contains no secrets and grants no access by itself.
A directory rename or move keeps the same association.

A clone on another machine has the same ID but needs its own local values or an authorized cloud pull.
Deleting the field creates a new association on the next write. It does not delete or recover the old secrets.

## Select an environment

```bash
lpm env set --env=development API_TOKEN=development-token
lpm env set --env=staging API_TOKEN=staging-token
lpm env list --env=staging
lpm dev
lpm run start
lpm run start --env=development
```

For each script, selection uses this order:

1. The command's `--env` value.
2. `tasks.<name>.env` in `lpm.json`.
3. The matching `env.<name>` mapping in `lpm.json`.
4. The default environment.

The example configuration selects `development` for `dev` and `staging` for `start`.
Explicit `--env=development` overrides that selection for one run. `--env=default` selects the default stored values.
Named values do not require matching dotenv files.

Each stored environment is independent. If a selected environment is missing or empty, runtime loading falls back to the default stored environment.
A nonempty named environment does not inherit missing keys from the default environment.
Explicit [lpm env get and list](/docs/dev/env#local-file-management) inspect the selected environment without this fallback.

## Files, stored values, and validation

The standard dotenv order is `.env`, `.env.local`, `.env.<name>`, then `.env.<name>.local`. Later files override earlier files.
Configured paths and [environment inheritance](/docs/reference/lpm-json#environments) can change that file selection.

Inherited process values take precedence over dotenv values. Stored secrets load after files and can override inherited process values.
Schema defaults fill missing values. An invalid required value stops startup.
Runtime hooks such as `NODE_OPTIONS` and `LD_PRELOAD` are excluded from project values and inherited script environments.

Inspect the resolved project values with [lpm env print](/docs/dev/env#print-the-resolved-environment):

```bash
lpm env print --env=staging --format=json
lpm env check --json
```

`print` includes plaintext secrets. `secret: true` masks diagnostics, not this explicit export.
For one run, `--no-env-check` skips schema checks and defaults. It still loads local secrets.

## Import existing dotenv files

```bash
lpm env import .env
lpm env import --env=staging .env.staging
lpm env list --env=staging
lpm env import --env=staging .env.staging --overwrite
```

Import preserves existing destination values unless you pass `--overwrite`.
The input file remains on disk. The CLI adds its path to `.gitignore`.
After you check the imported keys, remove secret values from the original file and restart the application.
Keep placeholders or non-secret examples in `.env.example`.

If `.env` is absent and `.env.example` exists, [lpm dev](/docs/dev/dev) copies the example to `.env`.
This copy contains example values. It does not export local secrets.

## Storage and recovery

| Platform | Local storage |
| --- | --- |
| macOS | Data Protection Keychain through an official signed CLI build. |
| Linux and Windows | Encrypted files in `~/.lpm/vaults/`. The encryption key uses native secure storage when available. |

On Linux, native key storage uses Secret Service. On Windows, it uses Credential Manager.
An unavailable native backend can use an existing file key at `~/.lpm/.vault-fallback-key`.
If native storage reports no key and cannot save a new one, initial storage can create a fallback file key.
Existing encrypted data still requires its original key.

Encrypted files need their matching encryption key. Copying encrypted files alone does not recover the values on another machine.
A missing or conflicting key produces an error. The CLI preserves existing data instead of silently replacing the key.

| Problem | Recovery |
| --- | --- |
| Values are absent. | Check the project directory, `vault` ID, and selected environment with `lpm env list --env=<name>`. |
| macOS denies access. | Use an [official signed CLI build](/docs/installation) and unlock the Keychain in your login session. |
| Native key storage is unavailable. | Restore access to Secret Service or Credential Manager, or restore the matching fallback key. |
| The fallback key is lost. | Restore the matching key from a trusted backup. An encrypted local file alone is insufficient. |
| A clone has no local values. | Import values or pull an authorized cloud copy before startup. |

Do not delete storage files or change the project ID to repair a missing encryption key.
For encrypted backup and access details, see [environment encryption and access](/docs/infra/secrets-vault).

## Changes take effect at startup

After you change a secret, restart the application through [lpm dev](/docs/dev/dev) or [lpm run](/docs/dev/run).
An existing process retains the values that it received at startup.
The application and its child processes can read those variables.

## Optional cloud sync

```bash
lpm env push --yes
lpm env pull --yes
lpm env pull --org=acme
```

Cloud sync requires an eligible LPM.dev Registry plan and authorized keys.
A pull replaces local values with the remote payload. Export local values that you need to preserve before a pull.
Runtime startup reads local values. It does not automatically pull cloud changes.
See [lpm env cloud sync](/docs/dev/env#cloud-sync) for personal sync, organization sharing, pairing, and CI access.
