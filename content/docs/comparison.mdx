Compare **npm**, **pnpm**, **Bun**, and **LPM CLI** by their defaults and supported workflows.

All four support npm packages and private registries. LPM CLI also coordinates development tools, local infrastructure, and optional LPM.dev Registry services.

The feature tables use the [source snapshots listed below](#source-scope). A dash means no built-in equivalent in that snapshot. External tools can extend each package manager.

## Security defaults

These defaults apply to dependency packages. Root and workspace lifecycle scripts have separate rules and can still run.

| Control | <PackageManagerLabel manager="npm">npm</PackageManagerLabel> | <PackageManagerLabel manager="pnpm">pnpm</PackageManagerLabel> | <PackageManagerLabel manager="bun">Bun</PackageManagerLabel> | <PackageManagerLabel manager="lpm">LPM CLI</PackageManagerLabel> |
| --- | --- | --- | --- | --- |
| Dependency lifecycle scripts | Blocked unless approved through `allowScripts` or `npm approve-scripts`. | Blocked unless approved through `allowBuilds` or `pnpm approve-builds`. Unreviewed builds fail the install by default. | Runs scripts for explicitly trusted packages, or its bundled trusted list when no explicit list exists. | Blocked until trusted. [lpm approve-scripts](/docs/packages/approve-scripts) saves approvals. [lpm rebuild](/docs/packages/rebuild) runs eligible scripts. |
| OS sandbox for dependency scripts | — | — | — | Filesystem restrictions and filtered environment. Outbound network is allowed by default. Strict mode denies it. |
| Minimum release age | Off. Configurable with `min-release-age` in days. | Prefers versions at least one day old. The default can fall back to younger versions. | Off. Configurable with `minimumReleaseAge` in seconds. | Off. Configurable [release cooldown](/docs/packages/install#recently-published-packages), with direct or strict transitive policy. |
| Dependency `engines.node` | Warns by default. `engine-strict` can reject mismatches. | Warns by default. `engineStrict` can reject mismatches. | No install-time enforcement. | [Enforced by default](/docs/packages/install#engines-enforcement). Required incompatible dependencies fail. Optional-only incompatible packages are skipped. |
| Vulnerability audit | `npm audit`. Registry advisory reporting also runs during install by default. | `pnpm audit`, using registry advisory data. | `bun audit`, using registry advisory data. | [lpm audit](/docs/packages/audit), using OSV and source analysis. Automatic post-install audit is opt-in. |
| Registry signature verification | `npm audit signatures` also verifies available provenance attestations. | `pnpm audit signatures` verifies registry signatures. | — | [lpm audit signatures](/docs/packages/audit#registry-signatures). Install-time signature enforcement is opt-in. |
| Install-time provenance policy | Attestation verification is a separate audit operation. | Optional `trustPolicy: no-downgrade` compares publication metadata. | — | Saved artifact approvals can trigger provenance verification and publisher-drift checks. Wider verification and no-downgrade policy are opt-in. |
| Custom install checks | Manifest extension hooks. | pnpmfile hooks. | Optional security scanner package, configured in `bunfig.toml`. | Optional [LPM Firewall](/docs/guides/firewall), source analysis, and local [policy extensions](/docs/infra/policy). |

A script approval permits execution. It does not prove that a package is safe. Bun's explicit `trustedDependencies` replaces its fallback list. An empty list blocks all dependency scripts.

LPM CLI keeps script eligibility separate from execution. Approved scripts run through rebuild or the install [auto-build rules](/docs/packages/install#dependency-scripts). Root-project scripts do not use the dependency sandbox. Sandbox support depends on the operating system. An approved degraded mode can reduce isolation.

LPM CLI does not verify every package's provenance by default. Its default scope covers saved artifact approvals, and unavailable evidence is best-effort. Available invalid evidence fails verification. See [signature and provenance configuration](/docs/reference/config-toml#integrity-and-package-verification).

LPM CLI can require [security approval](/docs/infra/security) before accepting weaker settings. Repository configuration cannot silently lower an approved security policy.

pnpm's built-in release-age preference differs from an explicit policy. Setting `minimumReleaseAge` makes strict enforcement the default unless `minimumReleaseAgeStrict` overrides it. Publication metadata ranking and cryptographic provenance verification are different checks.

## Installs, storage, and lockfiles

| Capability | <PackageManagerLabel manager="npm">npm</PackageManagerLabel> | <PackageManagerLabel manager="pnpm">pnpm</PackageManagerLabel> | <PackageManagerLabel manager="bun">Bun</PackageManagerLabel> | <PackageManagerLabel manager="lpm">LPM CLI</PackageManagerLabel> |
| --- | --- | --- | --- | --- |
| Default `node_modules` layout | Hoisted. `linked`, `nested`, and `shallow` are alternatives. | Isolated, with a symlinked virtual store. Hoisted and PnP layouts are alternatives. | New single-package projects use hoisted. New workspaces use isolated. Older Bun lockfiles and npm/Yarn migrations can retain hoisted defaults. | Hoisted for single-package projects. Isolated for workspaces and default installs with peer conflicts. [Configurable linker](/docs/packages/install#how-it-works). |
| Package storage | Content-addressable download cache. | Content-addressable package store. Hardlinks, reflinks, or copies. | Global package/version cache. Clones, hardlinks, or copies. Optional shared virtual store for isolated installs. | [Content-addressable store](/docs/packages/content-addressable-store). Copy-on-write clones or reflinks where available, with independent copies as fallback. |
| Lockfile | `package-lock.json`. Normally format 3, with format 4 for patches and manifest extensions. | `pnpm-lock.yaml`, format 9. | Text `bun.lock` for new projects. Existing `bun.lockb` remains supported. | Authoritative TOML `lpm.lock`. Generated `lpm.lockb` companion when the graph supports it. |
| Frozen install command | `npm ci` | `pnpm install --frozen-lockfile` | `bun ci` | [lpm install --frozen-lockfile](/docs/packages/install#frozen-lockfile-and-ci) |
| Prepare dependencies for other platforms | `--os`, `--cpu`, and `--libc` override the install target. | `supportedArchitectures` retains optional packages for selected OS, CPU, and libc combinations. | Multiple `--os` and `--cpu` values select optional packages for several targets. | [lpm fetch --platform](/docs/packages/fetch#platform-selection) fills the store for one target from the lockfile, without creating `node_modules`. |
| Dependency patches | `npm patch add` / `npm patch commit` | `pnpm patch` / `pnpm patch-commit` | `bun patch` / `bun patch --commit` | [lpm patch](/docs/packages/patch) / [lpm patch-commit](/docs/packages/patch#edit-and-commit-a-patch) |
| Dependency overrides | `overrides` | `overrides` | `overrides` and `resolutions` | npm `overrides`, Yarn `resolutions`, and `lpm.overrides`. |
| Reusable dependency build artifacts | — | Side-effects cache enabled by default. Optional remote dependency-build cache. | — | Automatic [native build cache](/docs/packages/rebuild#native-build-cache) for eligible strict-sandbox builds on macOS and Linux. |
| Lockfile migration | Can use Yarn lock data during installation. | `pnpm import` reads npm and Yarn lockfiles. | Imports npm, Yarn, and pnpm lockfiles. `bun pm migrate` can run without installing. | [lpm migrate](/docs/packages/migrate) imports npm, pnpm, Yarn, and Bun lockfiles. |

Layout names do not guarantee identical dependency visibility. pnpm privately hoists dependencies by default. LPM CLI's hoisted layout exposes direct dependencies at the root and uses package-local dependency links. See [dependency layouts](/docs/packages/install#how-it-works).

Migration support depends on the source lockfile format and its features. The migration guides describe supported inputs and project changes.

Preparing packages for another platform does not make its native build scripts runnable on the host. LPM CLI fetches only packages already present in the lockfile.

| Dependency manifest repairs | Declarative `packageExtensions`, or `.npm-extension.mjs` / `.npm-extension.cjs` hooks. | `packageExtensions` adds missing declarations. `.pnpmfile.mjs` / `.pnpmfile.cjs` hooks support programmable transformations. | — | [Policy extensions](/docs/infra/policy) can allow, warn, or block candidates. They do not transform manifests. |
| Copy package source into a project | — | — | — | [lpm add](/docs/packages/add), for supported registry packages. |

Catalogs share version declarations across workspace members. They differ from overrides, which can replace dependency requirements in the resolved graph.

Source-usage analysis differs from pruning packages that are no longer declared. Static inspection can miss framework conventions or dynamic imports. [Tidy exclusions](/docs/packages/tidy#ignore-intentional-dependencies) preserve intentional dependencies.

## Development tools and infrastructure

Bun includes its own JavaScript runtime, bundler, and test engine. LPM CLI manages runtimes and external tools, then coordinates their execution.

| Capability | <PackageManagerLabel manager="npm">npm</PackageManagerLabel> | <PackageManagerLabel manager="pnpm">pnpm</PackageManagerLabel> | <PackageManagerLabel manager="bun">Bun</PackageManagerLabel> | <PackageManagerLabel manager="lpm">LPM CLI</PackageManagerLabel> |
| --- | --- | --- | --- | --- |
| Package scripts and one-off tools | `npm run`, `npm exec`, `npx` | `pnpm run`, `pnpm exec`, `pnpm dlx` | `bun run`, `bunx` | [lpm run](/docs/dev/run), [lpm exec](/docs/dev/exec), [lpm dlx](/docs/dev/dlx). |
| Runtime management | Uses the installed Node.js runtime. | Manages Node.js, Bun, and Deno through `pnpm runtime`. | Built-in JavaScript and TypeScript runtime. | Manages Node.js and Bun through [runtime configuration](/docs/dev/node-version-pinning). |
| Project package-manager version | Uses the invoked npm version. `devEngines` can enforce requirements. | Automatically downloads and uses the requested pnpm version from project metadata. | Uses the invoked Bun version. | Uses the invoked LPM CLI version. |
| Task dependencies and result caching | Run scripts. Use a separate task-cache tool. | `pnpm pipeline` provides task dependencies and a local result cache. | Parallel and sequential script execution. No task-result cache. | [Task graph and local cache](/docs/dev/task-runner), with optional [remote cache](/docs/infra/remote-cache). |
| Bundling | Project tooling. | Project tooling. | Built-in `bun build`. | [lpm bundle](/docs/dev/bundle) manages Rolldown. [lpm pack](/docs/dev/pack) runs project-local tsdown. |
| Standalone executables | Separate Node.js or project tooling. | `pnpm pack-app` embeds a CommonJS entry and Node.js through Node SEA. | `bun build --compile` bundles application code and the Bun runtime, with cross-compilation and embedded assets. | Separate runtime or project tooling. |
| Test execution | `npm test` runs a package script. | `pnpm test` runs a package script. | Built-in `bun test`. | [lpm test](/docs/dev/test) runs supported project test tools such as Vitest, Jest, and Mocha. |
| Linting, formatting, and type checking | Project tooling. | Project tooling. | Project tooling. TypeScript execution does not check types. | [lpm lint](/docs/dev/lint) and [lpm fmt](/docs/dev/fmt) manage Oxlint and Biome. [lpm check](/docs/dev/check) runs local `tsc` or managed `tsgo`. |
| Development server | Project scripts. | Project scripts. | HTML entrypoints and full-stack serving with hot-module replacement. | [lpm dev](/docs/dev/dev) coordinates servers, dependencies, services, environment variables, and readiness. [Port management](/docs/infra/port-management) handles conflicts and supplies service URLs and ports. |
| Diagnosis and supported repairs | `npm doctor` examines the registry connection, versions, permissions, and cache. | `pnpm doctor` examines installation, filesystem, runtime, and registry state. | No general doctor command. | [lpm doctor](/docs/infra/doctor) examines project, runtime, tool, and security state. `--fix` applies supported repairs. |
| Skill integration | External tools. | External tools. | External tools. | [lpm skills](/docs/packages/skills) manages standalone skills. Approved LPM.dev package guidance follows selected dependency versions. |
| Secrets | Environment variables or external tools. | Environment variables or external tools. | Automatic `.env` loading and OS-backed `Bun.secrets` APIs. | [Encrypted environment vault](/docs/infra/secrets-vault), with optional team and cloud synchronization. |
| Local certificate authority | External tools. | External tools. | External tools. HTTPS serving accepts certificates. | [Local HTTPS](/docs/infra/local-https) with certificate generation and trust management. |
| Public tunnels to localhost | External tools. | External tools. | External tools. | [Tunneling](/docs/infra/tunneling), domain claims, and webhook inspection through LPM.dev Registry. |

pnpm's optional remote dependency-build cache stores package installation artifacts. It is separate from the local task-result cache in `pnpm pipeline`.

By default, `pnpm run` and `pnpm exec` check installed dependencies and install when needed. `verifyDepsBeforeRun` configures this behavior. The check does not support PnP layouts.

pnpm reads its requested version from `devEngines.packageManager` or `packageManager`. When Corepack invokes pnpm, pnpm leaves version selection to Corepack.

Bun also provides application APIs for PostgreSQL, MySQL/MariaDB, SQLite, Redis, and S3. These APIs run inside application code. They do not provision database servers. Applications launched through npm, pnpm, or LPM CLI can use their selected runtime's APIs and external libraries.

Standalone executables have target and dependency constraints. pnpm's Node SEA workflow requires a supported Node.js version and a CommonJS entry. Bun's cross-compilation also needs dependencies suitable for the target.

LPM CLI's automatic package guidance applies to approved skills on direct LPM.dev Registry dependencies. [Standalone skills](/docs/reference/ai-agent-skills#manage-standalone-skills) have separate installation and update workflows.

LPM CLI's local tools work without an LPM.dev Registry account. Hosted tunnels, environment synchronization, and hosted remote caching require the relevant service access.

## Publishing and registries

All four tools support npm-compatible registries and scoped registry configuration. LPM CLI sends ordinary npm packages to npmjs.org by default. Only `@lpm.dev/*` always routes through LPM.dev Registry. See [registry routing](/docs/registries).

| Capability | <PackageManagerLabel manager="npm">npm</PackageManagerLabel> | <PackageManagerLabel manager="pnpm">pnpm</PackageManagerLabel> | <PackageManagerLabel manager="bun">Bun</PackageManagerLabel> | <PackageManagerLabel manager="lpm">LPM CLI</PackageManagerLabel> |
| --- | --- | --- | --- | --- |
| Publish to an npm-compatible registry | `npm publish` | `pnpm publish` | `bun publish` | [lpm publish](/docs/packages/publish), with registry selection. |
| Stage a release for approval | `npm stage` | `pnpm stage` | — | [lpm stage](/docs/packages/stage) supports upload, inspection, download, approval, and rejection. |
| Publish provenance | `--provenance`. Also automatic for eligible trusted publishing. | `--provenance`. Also automatic for eligible trusted publishing. | — | `--provenance`, with supported CI identity. |
| npm trusted publishing | GitHub Actions, GitLab CI, and CircleCI token exchange. | GitHub Actions identity requests or a supplied `NPM_ID_TOKEN`. | — | GitHub Actions identity requests or a supplied `NPM_ID_TOKEN`, including GitLab CI. |
| Swift packages | — | — | — | [Swift package installation and registry configuration](/docs/packages/swift-package-registry). |
| OTP when the registry requires it | Supported. | Supported. | Supported. | Supported. |
| Registry credential configuration | `.npmrc`, including environment substitution. | Login writes global `config.yaml`. `.npmrc` compatibility remains. | `.npmrc` or `bunfig.toml`, including environment-backed credentials. | OS secure store preferred, encrypted-file fallback, and [`.npmrc` compatibility](/docs/infra/authentication). |

Trusted publishing requires registry-side configuration for the package and CI identity. Token exchange and provenance generation have separate requirements. For example, npm's CircleCI exchange does not automatically generate provenance.

Staged publishing requires a registry that implements the npm staging API. The upload remains separate from approval and public availability.

LPM.dev Registry is an optional publishing destination. Packages are private by default, with Free, Pool, and Marketplace distribution available through explicit settings. See [package distribution](/docs/packages/package-distribution).

pnpm also provides pnpr, an optional registry server for resolution, package delivery, and dependency-build caching. It is separate from the public npm registry.
